# Локальный контекст задачи: мониторинг BMS EnBMS

Папка `enBms/` в репозитории `sunReceiver`. Здесь — локальный контекст задачи
(решения, ссылки, заметки), чтобы не терять детали между сессиями.

## Источники

- Протокол EnBMS: `/home/sasha/src/energybms/PROTOCOL.md`
- Живой срез устройства: `/home/sasha/src/energybms/DEVICE_SNAPSHOT.md`
- Реверс/инструменты: `/home/sasha/src/energybms/REVERSE_ENGINEERING.md`,
  `tools/query_bms.py`

## Ключевые решения

1. **Модель кода**: BT-транспорт (соединение/поддержание/восстановление/ошибки)
   взят из модуля CE308 (`ce308_client.go`, `ce308_agent_linux.go`); опрос/хранение/
   усреднение — из модуля ANT BMS (`bms_poller.go`, `bms_accumulator.go`,
   `redis_store.go`, `pg_store.go`).
2. **Ключ устройства — MAC** (BLE-имя `BP00` не уникально). В Redis HASH
   `sunreceiver:enbms:current` поле = MAC; `name` — только отображение.
3. **Читаем только Battery** (CID2 `0x61`).
4. **Формат кадра (важно!)**. Реальный кадр (проверено CRC-16/CCITT на живых
   кадрах Battery и BasicInfo, снятых bleak с устройства):
   `Запрос: 7E 10 ADR 46 CID2 LEN(2) INFO(с 7) CHKSUM 0D`;
   `Ответ:  7E 14 ADR CID2 RTN LEN(2) INFO(с 7) CHKSUM(2) 0D`;
   полная длина = `10 + LENID`, `LENID = frame[5]<<8 | frame[6]`.
   В `PROTOCOL.md` §3.1 указано «9 + LENID», а в `DEVICE_SNAPSHOT.md` полные
   кадры приведены без байта `RTN` — таблица/кадры документов неточны,
   ориентироваться на живой кадр. Сборка — строго по длине (в payload
   встречается `0x0D`).
5. **Соединения постоянные**, переподключение с бэкоффом 2…30 с; ретрай таймаута
   чтения до 3 попыток; после 3 подряд неудач — реконнект.
6. **Последовательный опрос**, цикл ≤ 1/с.
7. **Лимит BT-устройств** `enbmsMaxBTDevices = 5` (EnBMS + CE308); при превышении
   опрос EnBMS не стартует. Значение подлежит уточнению на конкретном адаптере.
8. **Хранение**: Redis `sunreceiver:enbms:current` (HASH) + ряд
   `sunreceiver:enbms:series:<YYYY-MM>` (5-мин точки); PG `sunreceiver.enbms_averages`.
   Неполный промежуток при остановке — только в Redis.

## Дашборд (сделано по запросу пользователя)

Изначально задача ограничивалась пулером («фронт/бэкенд не трогаем»), но отдельным
запросом EnBMS выведен на дашборд:
- бэкенд: `/api/bms`, `/api/bms/<mac>`, `/api/bms/<mac>/series` отдают EnBMS,
  приведённый к формам `bmsDevice`/`bmsSeriesPoint`, с `kind="enbms"`;
  `ShowBMS` включается и при настроенном enBms;
- фронт: заголовки обобщены, `kind` в `bms.js` управляет подписями и скрытием
  блока мощностных ключей и примечания по датчикам; подписи температур для EnBMS
  нейтральные.

## Проверки

- `go build ./...`, `go vet ./...`, `go test ./...` — зелёные.
- Тесты: `enBms_test.go` (кадр/CRC/парсинг живого payload, реальный кадр

- Живая проверка на проде (192.168.0.x): после деплоя пулер подключается к

  5 минут формируется усреднённая точка в `sunreceiver:enbms:series` и PG
  `sunreceiver.enbms_averages`.

## Замечания по эксплуатации

- При старте два BLE-пулера (CE308 и EnBMS) одновременно пытаются подключиться;
  возможен разовый таймаут Connect (20 с) у одного из них — затем он
  переподключается сам. Доступ к глобальному `bluetooth.DefaultAdapter`
  синхронизирован мьютексом `btAdapterSetupMu` (и запись `ce308EnsurePowered`, и
  чтение через `btDefaultAdapter`); сами Connect не сериализуются
  (самовосстанавливается).
- При остановке сервиса на .253 для BLE-диагностики помнить правило
  `.kilo/AGENTS-private.md`: останавливать `sunreceiver.service` и запускать
  обратно после теста.
