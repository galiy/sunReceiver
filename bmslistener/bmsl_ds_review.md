## Вердикт в целом

Код компактный, честный, и главное структурно верное — парсинг и
ресинхронизация потока сделаны правильно, shm-формат совпадает с экосистемой
mapd/mpptd, «не трогать TX / не трогать чужие порты» соблюдено. Но есть
**3 реальных бага в парсинге/цикле** и **2 эксплуатационные ловушки**, которые
закрыть до выкатки web-api.

---

## Высокий приоритет (баги)

### 1. `power_w` парсится как int16, а по спецификации поле 4 байта (int32)
`bmslistener.c:260`:
```c
d->power_w = (double)(int16_t)rd16be(f, 111);
```
В `antbms-protocol-status-frame.md` поле `Current Power` на offset 111 —
**4 байта, int**. Если BMS кладёт 202 W как `00 00 00 CA` (BE), то 16-битное
чтение даёт `0x0000` = 0. Это **ровно объясняет наблюдение из worklog**
«в JSON выдаётся 0.0 при ненулевом токе» — поле не «не проброшено», а
читается старшее слово от нуля. Исправление: `(double)(int32_t)rd32be(f, 111)`.

### 2. Температуры парсятся без знака, по спецификации — `short` (signed)
`bmslistener.c:252-255`:
```c
d->temps[i] = rd16be(f, off);  /* °C int16 */
```
Комментарий говорит int16, но `rd16be` возвращает `uint16_t`. Ниже нуля
(зимнее хранение, LiFePO4) −5 °C → `0xFFFB` → в JSON `65531`.
Исправление: `(int16_t)rd16be(...)`.

### 3. Busy-loop: 100% CPU, пока подключено ≥1 устройство
`service_fds` (`bmslistener.c:453-479`) читает через `read()` на fd с
`O_NONBLOCK` — при пустом буфере tty приходит мгновенный `EAGAIN`, цикл
выходит, и `if (!any) millisleep(...)` (`:478`) срабатывает **только когда
устройств нет вообще**. При наличии устройств главный цикл (`:507-527`)
крутится на полной частоте ядра между burst-ами по 140 байт (раз в 250 мс) —
это **чистый спин на одном ядре Малины 24/7** (тепло, питание, троттлинг).

Исправление (с учётом того, что `select()` на этой плате не работает — из
worklog): в `service_fds` вести флаг «данных не было ни с одного порта» и
спать 10–20 мс, либо открыть fd в блокирующем режиме с `VMIN=0, VTIME=2`
(read сам ждёт до 200 мс). Латентность ≤20 мс при периоде кадра 250 мс —
не критична.

### 4. Проба (probe) блокирует весь цикл до 7 с на порт + бесконечный цикл пробы молчащих адаптеров
- `dev_is_bms` (`:314-335`) — синхронный цикл чтения до 7 с; за это время
  `service_fds` не ходит, данные живых BMS копятся в буфере tty (на старом
  ядре Jessie лимит ~4 КБ → потеря кадров, хотя ресинхронизация быстрая).
- Хуже: BMS **сама не вещает** (только в ответ на `5A5A` дисплея —
  зафиксировано в worklog). Если дисплей выключен, адаптер физически
  присутствует, но молчит → каждый `scan_for_new` (30 с) заново гоняет
  7-секундную пробу «NOT ant bms» — **навсегда**. Два таких адаптера =
  14 с стаппа из каждых 30 с основного цикла; при нескольких неизвестных
  портах суммарный стапп может превысить `SILENCE_TIMEOUT` (30 с) и живые
  устройства будут забываться/переподключаться.

Исправление: (а) экспоненциальный бэк-офф повторных пробы для портов,
проваливших пробу (напр., не раньше чем через 5 мин); (б) ограничить
суммарное время проб за один scan (напр., ≤3 с); (в) желательно — пробовать
порт только после краткой (1–2 с) предварительной проверки.

### 5. systemd: `Restart=always` — сервис нельзя остановить `systemctl stop`
`bmslistener.service:9-10`. `Restart=always` перезапускает юнит **и после
чистого выхода** (exit 0 по SIGTERM). То есть `systemctl stop bmslistener` →
процесс умирает → через 3 с поднимается снова. Остановить можно только
`disable --now`/`mask` — это ловушка для эксплуатации. К тому же при
crash-лупе `RestartSec=3` даёт повторный open/close PL2303 каждые 3 с, а
worklog прямо предупреждает, что лишние open/close деградируют адаптер.
Рекомендую `Restart=on-failure` (+ при желании `StartLimitIntervalSec=60`,
`StartLimitBurst=5`).

## Средний приоритет

### 6. `pend` не инициализируется в `dev_is_bms` и в `main`
`bmslistener.c:317` (`memset(&t, 0, …)`) и `:503-504` — `pend` становится
`0`, а не `-1`. В `main` это закрывается `bms_reset` перед активацией слота,
а в probe даёт лишний «фейковый» парсинг первых 140 байт (безвредно для
исхода пробы, но хрупко: логика «0 = нет маркера» становится неявной).
Явно инициализировать `pend = -1` в обоих местах (или вынести конструктор
`bmsdev_init`).

### 7. Truncation JSON при большом числе устройств → невалидный JSON молча
`SHM_SIZE = 8192` (`:75`), `BUFADD` (`:352-354`) при переполнении просто
обрывает вывод. Расчёт: ~500–560 байт на устройство с 16–32 ячейками →
**~14–15 устройств — уже обрезка посреди числа**, без закрывающего `]` →
потребитель получает битый JSON. `MAX_DEVS=32` при 8 КБ недостижим.
Варианты: поднять сегмент до 16–32 КБ (формат «json + #EOF» это позволяет),
либо честно останавливать сериализацию с маркером `"truncated":true`. Плюс:
добавить в JSON верхнеуровневое поле времени публикации (напр.,
`"updated":<epoch>`) — сейчас потребитель детектит «мертвого» производителя
только по сталеющим per-device `timestamp`, а это работает только пока
устройства были активны.

### 8. TOCTOU-гонка с usbscanner и другими демонами на новых ttyUSB*
Проверка занятости (`port_in_use_by_other`, `:130-162`) — снимок `/proc` в
момент скана; между проверкой (`:422`) и `open` (`dev_is_bms`) чужой демон
может открыть тот же tty — байты входа tty **делятся между двумя читателями**
(оба получат мусор), а наш `tcsetattr(19200)` (`port_config`) может задеть
пробную скорость usbscanner (19200/57600/115200). В проде сработало (MAP
занятым пропускается), но для порта, который usbscanner ещё не «присвоил»
демон (D0-устройства — как раз наш случай, и будущие MPPT/зарядки), гонка
реальна. Дешёвое усиление: пропускать порты, присутствующие в
`/var/map/devices_found` с кодом `D5`/`D7`/`D9` (известные чужие типы), и/или
сравнивать `st_dev+st_ino` device-узла на момент открытия.

### 9. Первое снятие нового устройства публикуется с нулями
`scan_for_new` (`:443`) ставит `b->last_ok = now_ts()` до первого
разобранного кадра, а `publish_all` (`:360-362`) пропускает только
`last_ok == 0` → до первого реального кадра (≤250 мс, т.к. дисплей опрашивает
сам) в shm уходит один снимок с `cells_v=0.000, soc=0`. Лечится простым
`if (d->frames_ok == 0) continue;` в `publish_all` (или копированием
разобранного состояния из probe-структуры `t` в слот).

## Низкий приоритет / заметки

1. **`cell_count` с fallback 16** (`:236`) — магическое число. Лучше clamp:
   `if (cc < 1) cc = 1; if (cc > 32) cc = 32;`
2. **`CLOCAL` принудительно сброшен** (`:185`) — на этой плате работает, но
   `CLOCAL=0` + потерянный carrier на других PL2303-вариантах означает
   «вход отключён». Осознанный выбор — ок, но стоит закомментировать, что это
   проверено именно на этом железе (сейчас комментарий про «мягкую настройку»
   про это молчит).
3. **`/tmp/bmslistener.log` без ротации** (`:52`) — при регулярных событиях
   (probe/reap/scan) файл будет расти; на Jessie-Малине `/tmp` чистят
   tmpfiles, но явное ограничение (размер/количество) не помешает.
4. **`memmove` с нулевой длиной** (`:302`) — при `rxlen == pend+140` `src`
   указывает за конец массива (n=0, на практике безвредно, формально UB).
   Не критично.
5. **Комментарий про `#EOF` в `publish_all`** (`:398-399`) — путаный: размер
   данных нигде не фиксируется, сегмент читается целиком с NUL-терминацией
   после `memset`. Комментарий лучше переписать под фактическую модель.
6. **`devs[32]` на стеке ~136 КБ** (`:502`) — для main-нити ок, но при
   будущем переносе в поток (800 КБ по умолчанию) впритык.

## Что сделано правильно (подтверждено)

- **CRC**: сумма байт 4..137, сравнение с BE u16 на offset 138 — точно по
  спецификации, совпадает с эталоном (5767). ✓
- **Ресинхронизация `bms_feed`**: поиск маркера только между кадрами (не
  ложный захват маркера внутри данных), фиксированный сдвиг на 140 байт после
  каждого кадра (валидного или нет), CRC-гейт — поток самовосстанавливается
  после потерь/вставок байтов. ✓
- **Дисциплина по портам**: TX не пишется никогда, `tcflush`/сбросов нет
  (согласно полевому замечанию про деградацию PL2303), fd из probe
  передаётся без повторного open/close. ✓
- **Не конфликтует с экосистемой**: ключ shm 2018 (mapd/mpptd — 2015/2016),
  формат «JSON + #EOF» как у них, чужие порты пропускаются по rdev. ✓
- **Завершение**: корректный сигнал-флаг (async-signal-safe), fd
  закрываются, shm-сегмент намеренно остаётся (последнее состояние доступно
  читателю). ✓

## Разрывы в документации

- `antbms.md:13-14` и таблица скоростей (`:147-158`) до сих пор говорят
  «предположительно 9600 бод» для нашей платы — worklog уже доказательно
  решил **19200**. Заголовок документа противоречит его же разделу
  «РЕЗУЛЬТАТ».
- Worklog ссылается на `docs/antbms/scripts/antbms_passive.py` и
  `antbms_inject.py` — **файлов в репо нет** (есть только
  `antbms_init_monitor.py` и `antbms_poll.py`).
- Эталонные дампы (`dump_19200.bin`, boot2_*) по-прежнему не сохранены в репо
  (worklog: «по запросу») — без них парсер не воспроизводим. Рекомендую:
  закоммитить эталонный дамп в `docs/antbms/data/` и добавить в
  `bmslistener` режим `--selftest <file>` (пробросить поток через
  `bms_feed`/`bms_parse_frame` и напечатать кадры) — это и юнит-тест парсера,
  и регрессионный чек.
- `bmslistener/` пока **не в git** (untracked) — закоммитить вместе с фиксами.

## Итоговый чек-лист до web-api

1. `power_w` → `rd32be` (int32). 2. Температуры → `int16_t`. 3. Анти-спин в
   `service_fds` (sleep 10–20 мс при пустых read). 4. Бэк-офф/лимит времени
   пробы. 5. `Restart=on-failure`. 6. `pend=-1` явно. 7. Лимит/рост shm +
   `updated` в JSON. 8. `frames_ok>0` в `publish_all`. 9. Актуализировать
   `antbms.md` (19200), добить missing-скрипты и эталонный дамп, закоммитить
   `bmslistener/`.

Пункты 1–5 — обязательные; 6–8 — дешёвые и закрывают классические
edge-кейсы (переподключение, молчание, переполнение), которые и просил
проверить worklog.
