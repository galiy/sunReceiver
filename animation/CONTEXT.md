# Анимация — контекст

Цель: создать анимацию, отражающую работу солнечной электростанции (инверторы,
МАП, MPPT, счётчик, BMS, лампы-индикаторы и т.п.) на основе реальных данных
sunReceiver.

## Как работаем

- Пользователь скидывает **фото объекта или устройства**.
- Я делаю для него **стилизованное изображение** (SVG/PNG, единый стиль)
  и кладу в соответствующую папку.
- Стилизованные изображения далее используются как спрайты/элементы анимации.

## Структура папок

```
animation/
  CONTEXT.md      — этот файл (контекст, реестр, статус)
  objects/        — стилизованные изображения ОБЪЕКТОВ (дом, участок и т.п.)
  devices/        — стилизованные изображения УСТРОЙСТВ (инвертор, МАП, счётчик…)
  schemes/        — общие схемы (PlantUML, исходники .puml)
```

## Объект 1 — опора ЛЭП (`objects/power-line-pylon.svg`)

Итог по контрастному референсу — **фронтальный ажурный силуэт** (не перспектива):
- Жирный контур `#2c2f33` (stroke ~7), внутренняя решётка тоньше (~4);
- **Шпиль**: ажурная башенка, сужается кверху, с крестами и вершиной;
- **4 яруса траверс**: 2 малых у шпиля + 2 больших ниже (полки ровные,
  без поворотов — раньше rotate давал «волны»);
- **Гирлянды изоляторов**: вертикальный зигзаг-ромбик у краёв полок;
- **Мачта**: центральная стойка + 2 сильно расходящиеся книзу боковые ноги
  (+ 2 внутренних наклона для объёма) → читается сужение кверху;
- **Решётка**: кресты-раскосы блоками между горизонтальными поясами;
- **Основание**: 3 бетонных фундамента + трава.
- Провода: короткие сходящиеся линии с пролётами.

Главный урок: посадка/форма важнее «ракурса» — фронтальный ажурный
силуэт с контрастным жирным контуром даёт узнаваемую опору.

## Схемы (`schemes/`)

Общие схемы в виде **PlantUML** (исходники `.puml`, рендер — `plantuml -tsvg`).

Схемы нужны как **постановка задачи для страницы анимации дашборда**:
каждая связь — **анимированная линия**, по которой «бежит» ток, рядом
подписана **мощность**, обновляемая **раз в 1 секунду**. На связях помечено,
**откуда брать мощность** (тег/формула).

**Связи — ЛИНИИ (не стрелки)**: мощность может течь в обе стороны,
направление определяется знаком (±) подписанной величины.

### Схема 1 — дом (`schemes/scheme-house.puml`)

Топология (top-to-bottom):
- магистраль: **Сеть → Счётчик DDS238 → МАП**;
- **Дом подключён напрямую к МАП** (не к внутренней сети);
- **«Внутренняя сеть»** — объект-соединитель: соединяет **МАП** и **все
  инверторы (в доме)**; к каждому инвертору — **панель**;
- **под МАП — батарея LiFePO4**, к батарее — **все имеющиеся КЭС (MPPT)**,
  к каждому КЭС — **своя панель**.

Мощность на связях (источник тега):
| Связь | Откуда брать мощность |
|---|---|
| Панель — Инвертор | **P_PV инвертора** (у Deye `dc_total_power`; у Sofar `pv1_power`+`pv2_power`) |
| Панель — КЭС | **P_PV КЭС** (`pv1_power` = `P_PV`) |
| Инвертор — Внутр. сеть | **активная мощность инвертора** (`ac_active_power`) |
| КЭС — Батарея | **активная мощность КЭС** (`ac_active_power` = `P_Out`) |
| Внутр. сеть — МАП | **Σ активных мощностей всех инверторов** (сумма `ac_active_power`) |
| Батарея — МАП | **мощность по батарее** по данным МАП (`battery_power`) |
| МАП — Счётчик | **мощность сети** по данным МАП (`grid_power`) |
| Счётчик — Сеть | **мощность сети** по данным счётчика (`meter_active_power`) |
| **МАП — Дом** | **разница** (см. формулу ниже) |

**Формула мощности Дома:**

```
P_дом = Σac(инверторы дома) + grid_power + battery_power
```

где (знаки — как в контракте `values`):
- `Σac(инверторы дома)` = Σ `ac_active_power` всех инверторов дома (положительная при выработке);
- `grid_power` — мощность сети по данным МАП: **положительная при потреблении из
  сети, отрицательная при отдаче в сеть** — поэтому при отдаче она вычитается;
- `battery_power` — мощность батареи: **положительная при отдаче (разряде),
  отрицательная при заряде**.

Часть мощности, пришедшей в МАП из внутренней сети и от батареи, уходит в
сеть; **остаток — в дом**.

Согласование с записью «минус P(МАП→сеть)»: поскольку `grid_power` уже имеет
знак (минус = отдача в сеть), «− P(МАП→сеть)» в терминах безразмерной величины
отдачи эквивалентно `+ grid_power` в терминах тега со знаком. В коде
(`dashboard.go`, `buildAnimationResponse`) реализовано именно
`houseAC + MapGridPower + MapBatteryPower`.

### Схема 2 — гараж (`schemes/scheme-garage.puml`)

Топология: **Сеть → Счётчик CE308 (развилка) → Гараж**; счётчик CE308 — соединитель,
связывает **Сеть**, **Гараж** и **все инверторы (в гараже)**. Развилка — в точке
счётчика: одна линия **вправо в Гараж**, вторая **вниз к шине инверторов**;
к каждому инвертору — **панель**.

Мощность на связях:
| Связь | Откуда брать мощность |
|---|---|
| Сеть — Счётчик CE308 | **мощность счётчика CE308** (`ce308_active_power`, свежий снимок) |
| Счётчик — Гараж | **P_гараж = P(CE308) − Σac(инверторы)** (см. формулу) |
| Счётчик — шина инверторов | **Σ активных мощностей всех инверторов** (сумма `ac_active_power`) |
| Инвертор — шина | **активная мощность инвертора** (`ac_active_power`) |
| Панель — Инвертор | **P_PV инвертора** (у Deye `dc_total_power`; у Sofar `pv1_power`+`pv2_power`) |

**Формула мощности Гаража (справа от развилки):**

```
P_гараж = P(счётчик CE308) − Σac(инверторы гаража)
```

где (знаки — как в контракте `values`):
- `P(CE308)` — `ce308_active_power`: **положительная при потреблении из сети,
  отрицательная при отдаче в сеть**;
- `Σac(инверторы)` — Σ `ac_active_power` всех инверторов гаража (положительная при выработке) —
  поэтому при выработке она вычитается из потребления счётчика.

Пример постановки: сеть **+120 Вт**, инверторы **−1 Вт** → в гараж **+119 Вт**.

Примечание: если свежего снимка CE308 нет (счётчик не настроен/устарел) —

## Диагностика мощности батареи МАП (2026-09-21, утром) — ВЫВОДЫ

Пользователь не доверял `battery_power` (мощность по батарее, считаемая из данных
МАП): по его оценке дом потреблял ~1 кВт, а схема показывала ~3 кВт. Разобрано
по синхронным срезам (МАП + счётчик + инверторы + 2 BMS). Итог:

- **Формула в коде корректна**: `battery_power = −_PLoad_calc`, где
  `_PLoad_calc = Uacc × Iacc` (напряжение батареи × медианный ток `_IAcc_med_A_u16`).
  Проверено, что `|_PLoad_calc|` с точностью ~0,3–0,8% равен `Uacc × Iacc`
  (не «выработка инверторов + дом»).
- **Датчик тока МАП НЕ врёт**: `_Iacc` (130 А) ≈ сумма токов двух BMS
  (BMS-1 53,9 А + BMS-2 71,7 А = **125,6 А**), расхождение ~3,4%.
- **Счётчик и МАП по сетевой отдаче согласуются** (`_PNET_calc` vs `meter`).
- Следовательно батарея реально отдаёт **~6,5–6,8 кВт**, а дому идёт
  **~2,8–3,2 кВт** (не ~1 кВт). Четыре независимых источника (счётчик,
  инверторы, МАП-ток, 2 BMS) дают согласованную цифру.
- Гипотеза «завышена мощность по батарее» **не подтвердилась**.

**Пользователь с таким выводом не согласился** и указал: «На странице Графики
есть график мощностей» (проверить там). Вопрос остался **открытым** — сессия
оборвана. При продолжении сверить оценку «дом ~1 кВт» с графиком на странице

### 2. Скорость и количество огоньков зависят от мощности

Константы/хелперы в начале `animation.js`:
- `P_MIN=100`, `P_MAX=20000` (Вт) — шкала мощности.
- `pwLerp(v)` — `(abs(v)-P_MIN)/(P_MAX-P_MIN)` с зажимом в `[0,1]`:
  `|v|<=100 → 0` (режим 100 Вт), `|v|>=20000 → 1` (режим 20 кВт).
- `speedFor(t)` — px/с: `12` (100 Вт) .. `520` (20 кВт).
- `spacingFor(t)` — px **шаг между огоньками**: `SP_MAX=64` (100 Вт, редко) ..
  `SP_MIN=9` (20 кВт, вплотную). **Не зависит от длины линии**.
- `MAX_DOTS=60` — пул кружков на связь (запас для длинных линий).

`makeEdge` создаёт пул из `MAX_DOTS` кружков (r=4) на каждую связь.
`updateEdge` по знаку/величине задаёт цвет (зелёный/красный), направление и
**целевые** `tSpacing`/`tSpeed`.

### 3. Плавность (анти-дёрганье)

В `animateEdge(e, dt)` (вызывается из `loop` на каждый кадр с реальным `dt`):
- `spacing` и `speed` **плавно** (экспоненциально, `k=0.08`/кадр, ~0.3 с)
  приближаются к целям — без резких скачков при изменении мощности.
- Число огоньков `n = clamp(round(total/spacing), DOTS_MIN=2, MAX_DOTS)` — меняется
  **по одному** (следует из плавного шага), позиции непрерывны (без разрыва).
- Позиция хранится в диапазоне `[0,total)` — **не растёт бесконечно** (нет потери
  точности/Infinity).
- Раньше (до 2026-09-21 ~20:20) шаг задавался через длину линии (`total/…`), из-за
  чего на длинной линии огоньки разбегались даже при равной мощности; **исправлено** —
  шаг фиксирован по мощности, длиннее линия = больше огоньков.

### 4. Фикс зависания цикла анимации (критично)

**Симптом**: огоньки полностью пропадали. **Причина**: `getPointAtLength(не_конечное)`
бросал `TypeError: ... non-finite`, исключение рвало `requestAnimationFrame` — вся
анимация замирала. **Фикс**: защита от не-конечных значений — фолбэки для
`spacing/speed/tSpacing/tSpeed` (`SP_MAX`/`0`), `dt` ограничен `[0,0.1]`, проверка
`total>0 && isFinite(total)`, `if(!isFinite(s)) continue;` (точка с некорректной
позицией пропускается, цикл не падает). Прод-консоль после деплоя — чисто.

### Данные `/api/animation` (структура)

```json
{
  "generated_at": "…",
  "house": {
    "inverters": [{"name","kind","pv","ac","stale"}],
```

### Семантика знаков (важно для цвета/направления огоньков)

- `ac_active_power` положительная — выдача, отрицательная — потребление.
- `battery_power` при заряде отрицательная, при отдаче положительная.
- `grid_power`/`meter_active_power` — знак задаёт направление (в/из сети).
- Цвет огоньков: **из сети красный, выработка и в сеть зелёный**.

### Правило знака подписи мощности (схема, 2026-09-21)

Постановка пользователя: **потребление — `+`, выработка/отдача в сеть — `−`**.

В данных (контракт) знаки полей «исходные» (например: `ac_active_power` `+` при
выдаче, `battery_power` `+` при отдаче), но на схеме **подпись значения**
приводится к правилу пользователя отдельным множителем **`labelSign`** в `rule`
связи (в `animation.js`, обрабатывается в `updateEdge`):

- `labelSign: 1` — подпись как есть;
- `labelSign: -1` — подпись инвертирована к правилу пользователя.

`labelSign` влияет **только на текст подписи** (`fmtPower`) — цвет, направление
бега огоньков и активность связи по-прежнему считаются по сырому `value`.

Связи с `labelSign: -1` — это ветки выработки, где исходно выдача идёт `+`, но по
правилу должна быть `−`:
- Дом: «панель→инвертор» (pv), «инвертор→шина» (ac), «шина→МАП» (Σac);
- КЭС: «батарея→КЭС» (Σac КЭС), «КЭС→шина» (ac), «панель→КЭС» (pv);
- Гараж: «сеть→шина» (Σac), «шина→инверторы» (Σac), «инвертор→шина» (ac),
  «панель→инвертор» (pv).

Магистраль («счётчик→сеть» `meter_active_power`, «МАП→счётчик» `grid_power`,
«МАП→дом» `house_power`) и «батарея→МАП» (`−battery_power`) уже отдают подпись
по правилу пользователя (потребление `+`, отдача в сеть `−`) — `labelSign` там
не используется (`greenSign:-1`).

### Визуальные правила (от пользователя, 2026-09-20)

- **«Внутренняя сеть»** и **линия батареи** — это УЗЛЫ-СОЕДИНИТЕЛИ из UML (нужны
  только для формул расчёта), НЕ устройства. Изображаются как **шина**:
  - **без подписи**;
  - **ширина** определяется числом подключённых устройств;
  - **толщина** как у анимированной линии-связи.
- Все линии-связи с бегущими огоньками — **под прямыми углами**, углы **скруглены**
  (`pathWithRounds`, радиус 12).
- **Расстановка**: Сеть слева, Дом/Гараж справа, всё подключённое — ветвью вниз.

### Реализация в `animation.js`

- `buildScheme(container, nodes, edges)` — создаёт SVG, рисует связи (и шины) и
  спрайты; пересобирается только при изменении набора устройств (`ensureScheme`).
- `makeEdge` — ортогональный `path` (`pathWithRounds`) + подпись мощности + группа
  из 3 огоньков (`circle`, `getPointAtLength` для позиции).
- `drawBus` — горизонтальная шина (`line`, класс `.anim-bus-wire`).
- `updateEdge(e)` — по знаку `value` решает цвет (зелёный/красный) и направление
  бега (`toEnd`/`toStart` через `rule.greenDir`); `greenSign:+1` → v>0 зелёный,
  `greenSign:-1` → v<0 зелёный.
- `animateEdge` — на каждый кадр двигает огоньки вдоль пути (`path.getPointAtLength`).
- `layoutHouse` — магистраль сверху (Сеть→Счётчик→МАП→Дом, y=150), слева ветвь
  «Внутренняя сеть»(шина → инверторы → панели), справа ветвь батарея(шина)→КЭС→панели.
- `layoutGarage` — Сеть→шина→Гараж сверху, снизу инверторы→панели.
