# ANT BMS — расшифровка коммуникационного разъёма (HY2.0-8P)

Результат исследования распиновки коммуникационного (8-пинового) разъёма платы
ANT BMS модели **22PHB-TB-8-22S-240A** (OEM-плата 8–22S, до 230/240 А, Bluetooth,
производитель 蚂蚁兴能 / Qing Yun Hui Neng).

Уточнение: производитель не публикует открытый даташит с точной физической
раскладкой пинов. Ниже — распиновка, **согласованная по двум источникам**:
фото платы из чата + официальная страница ANT BMS «Wiring diagram Of ANT BMS
8S-22S 40A-230A Smart BMS» (`antbms.vip`). Значения пинов подтверждаются также
общей документацией коммуникационного порта ANT BMS
(«CAN или RS485 или UART используют один и тот же порт»). Скорость UART
протокола зависит от поколения прошивки; для платы **22PHB-TB-8-22S-240A** по замерам
2026-09-14 подтверждено **19200 бод** (см. раздел «Скорость UART-протокола ANT BMS»).

## Тип разъёма

- 8 контактов, называются **HY2.0-8P** (по расшифровке изображения) — это
  указывает на шаг **2.0 мм** (серия PH2.0/XH 2.0-совместимая). Подлежит
  проверке замером: если реальный шаг 1.25 мм — это серия **GH 1.25**.
  Шаг влияет на заказ ответного штекера под адаптер RS485.
- Разъём коммуникационный: к нему подключаются кнопка включения (SW),
  выносной дисплей (UART), а также выводятся CAN и RS485-интерфейсы для
  интеграции BMS в систему.

## Распиновка (согласовано по двум источникам)

| Пин | Обозначение | Функция | Примечание |
|-----|-------------|---------|------------|
| 1 | **B+** | Положительный полюс питания батареи | в подписи `B+` в вашем случае управляет питанием; на официальной схеме то же место помечено `B-` (OEM-вариант) |
| 2 | **SW** | Выключатель питания (Switch) | активация платы замыканием с общей линией |
| 3 | **ACC+** (на фото `+`) | Положительный сигнал активации / питание аксессуара | красный провод дисплея |
| 4 | **ACC−** (на фото `−`) | Отрицательный сигнал активации / общий (GND) | чёрный провод дисплея |
| 5 | **485A (TTL_TX)** (на фото `A`) | Линия A интерфейса RS-485 / **выход UART BMS (TX)** | жёлтый провод дисплея; данные BMS → наружу (маркировка в подписи «TTL_RX» — это точка зрения дисплея, у дисплея этот пин RX) |
| 6 | **485B (TTL_RX)** (на фото `B`) | Линия B интерфейса RS-485 / **вход UART BMS (RX)** | зелёный провод дисплея; данные внутрь BMS, сюда шлются команды (маркировка «TTL_TX» — точка зрения дисплея, у дисплея этот пин TX) |
| 7 | **CANH** | Высокий уровень шины CAN (CAN High) | свободен в нашей конфигурации |
| 8 | **CANL** | Низкий уровень шины CAN (CAN Low) | свободен в нашей конфигурации |

### Наблюдаемое в реальной конфигурации (22PHB-TB-8-22S-240A)

Как подключено на плате из чата:

- **Пины 1–2 (B+ и SW)** — кнопка включения (замыкание между ними = активация платы).
- **Пины 3–6 (ACC+/ACC−, A/B)** — выносной дисплей в порядке проводов:
  красный → ACC+ (пин 3), чёрный → ACC− (пин 4, GND), жёлтый → A/485A (пин 5),
  зелёный → B/485B (пин 6).
- **Пины 7–8 (CANH/CANL)** — свободны (зарезервированы под CAN-шину инвертора).

Соответствие цветов дисплея стандартной раскладке ANT: красный = VCC, чёрный =
GND, жёлтый = TX/UART (данные BMS → дисплей), зелёный = RX/UART (данные
дисплея → BMS).

## Особенности пинов 5/6 (485A/485B)

Важный нюанс: пины 5–6 подписаны как **«485A» и «485B»**, а на отладочной схеме
к ним добавлены метки «TTL_RX»/«TTL_TX» — но эти метки даны **с точки зрения
дисплея**, а не BMS. По фактическому подключению (и подтверждено:
п5/жёлтый отдаёт показания BMS, п6/зелёный принимает команды):

- **Пин 5 (485A, жёлтый)** = **выход UART BMS (TXD)** — отсюда BMS передаёт данные
  (показания V/A/W);
- **Пин 6 (485B, зелёный)** = **вход UART BMS (RXD)** — сюда приходят команды
  (от дисплея/тайчскрината или адаптера).

Здесь выведены **сырые TTL-уровни UART (3.3 В)**, а **не** готовая
дифференциальная RS485-пара (с драйвером/трансивером на плате).
Следствия:

- Инверторы ожидают дифференциальный RS485 (уровни A/B ±2–6 В). Подключать
  TTL-пины напрямую к шине RS485 инвертора **нельзя** — уровни несовместимы,
  есть риск повредить порт BMS.
- Для RS485-интеграции нужен **внешний адаптер TTL→RS485** (модуль на
  MAX485/MAX3485 или аналогичный):

```
BMS (пин 6, RXD)  ←  TTL_TX адаптера      (команды в BMS)
BMS (пин 5, TXD)  →  TTL_RX адаптера      (показания из BMS)
BMS (пин 4, ACC− GND) ─  GND адаптера
Адаптер A/B  ───────►  RS485 A/B инвертора
```

- Дисплей занимает тот же UART (пины 5–6). Для RS485-использования дисплей
  нужно **отключить** — два потребителя на одной TTL-линии конфликтуют.

## Подключение USB-serial адаптера для считывания данных

Для съёма данных с UART BMS (например, на плату ПАК «Малина» — Raspberry Pi)
используется внешний USB-адаптер TTL. В нашем примере — **PL2303TA с кабелем**
(USB-serial, чип PL2303). Цвета его проводов:

| Цвет | Сигнал адаптера |
|---|---|
| Красный | +5 В (выход питания адаптера) |
| Чёрный | GND |
| Белый | RXD (вход адаптера — принимает данные) |
| Зелёный | TXD (выход адаптера — передаёт данные) |

### Как подключить

Разрезаются провода, идущие на дисплей, и вместо дисплея подключается адаптер
(дисплей при этом отключается — это освобождает пины 5/6 под внешний UART).

Провода разъёма дисплея ↔ BMS (по распиновке):
- жёлтый → A (пин 5, 485A / TXD — **выход** BMS, показания наружу);
- зелёный → B (пин 6, 485B / RXD — **вход** BMS, приём команд);
- чёрный → ACC− (пин 4, GND);
- красный → ACC+ (пин 3, питание).

Подключение кабеля к разрезанным проводам (справленный вариант — по
фактическому подключению, уточнено на живом устройстве):

| Кабель PL2303TA | Провод дисплея (→ BMS пин) | Роль |
|---|---|---|
| **Чёрный (GND)** | Чёрный → пин 4 (ACC−, GND) | общий |
| **Белый (RXD — вход адаптера)** | Жёлтый → пин 5 (485A / TXD, **выход** BMS) | данные BMS → адаптер |
| **Зелёный (TXD — выход адаптера)** | Зелёный → пин 6 (485B / RXD, **вход** BMS) | данные адаптер → BMS |
| **Красный (+5 В)** | — не подключать | |

Соединение по **сигналам** — стандартный UART-кроссовер (TX↔RX): выход адаптера
(зелёный TXD) идёт на **вход BMS** (зелёный/пин 6); выход BMS (жёлтый/пин 5)
идёт на **вход адаптера** (белый RXD). Обратите внимание: по **цветам** провода
соединяются со своими же цветами (TXD адаптера·зелёный → зелёный BMS; RXD
адаптера·белый → жёлтый BMS) — это не «цветной» кроссовер, а корректное
попарное соединение TX/RX линий.

Предостережения:
- **Красный (+5 В) адаптера не подключается** — питание BMS идёт от батареи, подача
  внешних 5 В на порт может повредить вход BMS. Адаптер питается от USB (Малины).
- Контроль уровней: BMS UART — 3.3 В. Если адаптер выдаёт 5 В на сигнальных
  линиях (некоторые 5 В TTL-платы) — нужен делитель/уровневый буфер. При
  правильно выбранном PL2303TA-модуле UART-логика обычно уже 3.3 В на выводах,
  а 5 В подаётся только на питающий вывод (им и не пользуемся).
- Итог: красные (+5 В адаптера и + пина 3 дисплея) отрезаются/изолируются,
  используются только GND и две линии данных.

Проверка работоспособности на Малине (после подключения к последовательному
порту, напр. `/dev/ttyUSB0`): `stty -F /dev/ttyUSB0 19200 raw && cat /dev/ttyUSB0` —
при включённой BMS должен идти читаемый поток кадров (заголовок `A5 ...`).

## Скорость UART-протокола ANT BMS

Разные поколения ANT BMS используют **разные скорости** последовательного
протокола, и на уровне железа она не объявляется — определяется подбором
(или замером на осциллографе по ширине бита).

| Скорость | Где применяется |
|---|---|
| **19200 бод** | Классические/старые ANT BMS (протокол 2.x) — задокументированы в `syssi/esphome-ant-bms` (`baud_rate: 19200`) и RoboDurden/AntBms-Arduino. **Для нашей платы 22PHB-TB-8-22S-240A подтверждено замером 2026-09-14 (живой 140-кадр сходящимся CRC именно на 19200)** — см. `antbms-worklog.md`. |
| **9600 бод** | Некоторые OEM-платы и ANT-совместимые дисплеи/Bluetooth-модули — но не наша плата; проверка 19200→9600 давала побитый полусжатый поток (артефакт передискретизации). |

Для платы **22PHB-TB-8-22S-240A** рабочая скорость — **19200 бод** (проверено:
на 19200 идёт валидный поток, на 9600 — искажённый). Рекомендации:

- первым делом пробовать **19200 бод**: `stty -F <port> 19200 raw && cat <port>`;
- 9600 даёт мусорный полусжатый поток — переключить на 19200;
- при интеграции приложения (демон `bmslistener`) скорость жёстко 19200.

## Конфигурация Малины «до подключения BMS» (последовательные порты)

Снимок состояния последовательных портов ПАК «Малина» (192.168.13.60)
**до** подключения ANT BMS. Проверено по SSH 2026-09-14 (root, см.
`.kilo/malina-ssh.json`). Источник данных — `/var/map/devices_found`
(список устройств на шине, формируется демоном `usbscanner`),
`/var/map/devices_available.txt` (найденные USB-serial) и процессы на портах.

### Обнаруженные порты

| Порт (dev) | Аппаратура | Состояние в `devices_found` | Используется | Назначение |
|---|---|---|---|---|
| `/dev/ttyUSB0` | FTDI FT232R (USB-serial, VID:PID 0403:6001) | `D3R0` = **МАП (MAC)**, 19200 бод | да, демон `mapd` (PID) | шина МАП Титанатор |
| `/dev/ttyS0` (`= /dev/serial1`, mini-UART) | встроенный UART Raspberry Pi | `D0R0` = неопознано, 19200 бод | нет (демон не поднят) | не используется; при чтении даёт `Input/output error` |
| `/dev/ttyAMA0` (`= /dev/serial0`, PL011) | встроенный UART Raspberry Pi | не в списке | нет | не используется демонами (115200 — типичная настройка консоли) |

`devices_found` актуален на момент снимка:

```
/dev/ttyS0D0R0
/dev/ttyUSB0D3R0
```

### Расшифровка формата `devices_found`

Запись `<порт>D<тип>R<скорость>`:

- **D-код типа** (из `devices_found.pl` и `get_devices.sh`):
  - `D0` — неопознанное устройство (протокол не отвечает на запрос типа);
  - `D3` — **МАП / MAC** (это и есть Титанатор, `mapd`);
  - `D5` — **MPPT / КЭС-контроллер** (`mpptd`);
  - `D7`/`D9` — **CHARGER** (`chargerd`).
- **R-код скорости** (из `devices_found.pl`): `R0` = **19200**, `R1` = **57600**, `R2` = **115200** бод.

### Логика запуска демонов (tty_scan.sh)

`/usr/sbin/tty_scan.sh` (запускается `add_tty.service`):
1. ждёт 10 с и находит все `/dev/ttyUSB*` → `/var/map/devices_available.txt`;
2. запускает `usbscanner`, который опрашивает каждый USB-serial и `/dev/serial0`
   на скоростях 19200/57600/115200, устройство отвечает кодом типа → `devices_found`;
3. по коду типа запускает соответствующий демон:
   - `D3` (МАП) → `mapd`, `dbed`, `mserver`;
   - `D5` (MPPT) → `mpptd`;
   - `D7/D9` (CHARGER) → `chargerd`;
   - `D0` (неопознано) → **демон не запускается** (порт остаётся доступен как обычное char-устройство).

На момент снимка запущены `mapd` (МАП на ttyUSB0) и `batmond` (агрегатор
данных АКБ — обслуживает `read_json.php?device=bat`; отдельного serial-порта
не занимает, работает по агрегированной шине МАП через `mapd`). `mpptd`,
`chargerd` не запущены — в `devices_found` нет ни `D5`, ни `D7/D9`.

### Что это значит для подключения ANT BMS

- **Все USB-serial заняты**: единственный `ttyUSB0` — МАП. Вообще в этой системе
  **не подключено КЭС/MPPT-контроллеров**, поэтому соответствующих портов (и
  демона `mpptd`) сейчас нет. `read_json.php?device=mppt` в этом состоянии пуст.
  Если подключить КЭС — появится **новый `/dev/ttyUSB*`**, `usbscanner` опознает
  его как `D5` (MPPT), запустится `mpptd`, и именно опрос этого контроллера
  станет источником данных для API Малины (см. `docs/malina-web-api.md`).
- **Данные для API Малины берутся только с физически подключённых контроллеров**:
  пока КЭС нет в системе, их параметры не появятся в `read_json.php`, сколько бы
  раз ни опрашивался API. КЭС — отдельные USB-serial, а не «виртуальные» устройства.
- **Адаптер PL2303 (USB→UART) под BMS** при подключении к USB-порту Малины
  появится как **новый `/dev/ttyUSB1`** (FtDi останется ttyUSB0). Он будет
  просканирован `usbscanner`. Если ANT BMS не отвечает на запрос типа MicroArt —
  запишется как `D0` (неопознано), демоны не поднимутся, и порт останется
  доступен для чтения сторонним ПО (`cat`, `stty`).
- **Встроенные порты не подходят для этого подключения**: `ttyS0` даёт
  `Input/output error`, `ttyAMA0` демонами не обрабатывается; оба не обеспечат
  удобного доступа из приложения (и физически на разъём GPIO выведен только
  mini-UART/PL011 без готового кабеля). Поэтому целевой путь — **USB-serial
  адаптер → новый ttyUSB**.
- После подключения ВMS проверить пост физ. подключения: порт появится как
  `/dev/ttyUSB1` (или `/dev/ttyUSB0`, если МАП отключить), затем считывать
   поток: `stty -F /dev/ttyUSB1 19200 raw && cat /dev/ttyUSB1` (скорость — см.
  раздел «Скорость UART-протокола ANT BMS»).

| Параметр | CAN | RS485 (Modbus RTU) |
|----------|-----|---------------------|
| Линии | CANH, CANL | A, B (+GND) |
| Терминация | обязательно 120 Ом с двух концов шины | опционально, на длинных линиях 120 Ом |
| Топология | мульти-мастер, широковещательная | master–slave, адресный опрос |
| Протокол уровня | CAN 2.0 (ID, арбитраж, до 8/64 байт) | Modbus RTU (адрес, функция, CRC) |
| Проверка целостности | CRC аппаратно | CRC16 (ПО) |
| Инверторы | действуют «из коробки» (Deye/Growatt/Sunsynk и др.) | требуется выбор корректного протокола/адреса |

Для нашей платы: CAN выведен на пины 7–8 (готовая пара CAN-драйвера);
RS485 — только TTL-уровнем на пинах 5–6 (нужен внешний трансивер).
