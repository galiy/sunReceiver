# Электросчётчик DDS238 (мгновенные значения + посуточные тарифы)

Модуль опрашивает однофазный электросчётчик **DDS238** (Modbus TCP, holding registers)
и решает две задачи:

1. **Мгновенные значения** (напряжение, ток, мощность, …) в Redis + усреднённые
   5-минутные агрегаты в PostgreSQL — тот же принцип, что у МАП/MPPT («как для map»):
   опрос **1 раз в секунду**, в Redis через `SaveSnapshotWindow` (одна строка за каждые 10 с)
   за последние 2 календарных суток, в PG — усреднение общим аккумулятором
   (`accumulator.go`). Эти значения выводятся на **отдельной плашке в самом верху
   дашборда** (обновление 1 раз в секунду): напряжение, ток, активная/реактивная
   мощность, коэффициент мощности, частота, Import/Export/Total (состав плашки —
   из `METER_PARAMS` в `dashboard.go`, легко сократить).
2. **Посуточные тарифные значения**. Счётчик считает потребление из сети (`Import`)
   и отдачу в сеть (`Export`), но **не разводит по тарифам** «День/Ночь». Поэтому каждый
   день фиксируем показания на границах тарифной зоны и вычисляем 4 величины.

## Конфигурация

Отдельный файл **`dds238.json`** рядом с исполняемым файлом (как `sunReceiver.json`;
при `go run .` — fallback в CWD). Файл не коммитится в git; шаблон — **`dds238.json.sample`**
(в git, значения подставные).

```json
{
  "name": "Электросчётчик",
  "ip": "192.168.13.77",
  "port": 502,
  "unit": 1,
  "first_reg": 0,
  "register_count": 27
}
```

| Поле | Назначение |
|------|------------|
| `name` | Логическое имя (показывается в `values` / Redis current). |
| `ip`, `port` | Адрес счётчика / Modbus-TCP шлюза (по умолчанию порт 502). |
| `unit` | Modbus-адрес устройства (обычно 1). |
| `first_reg` / `register_count` | Блок читаемых регистров (по умолчанию 0..27). |

### Правила заполнения

- Копируйте `dds238.json.sample` → `dds238.json` и подставляйте реальные `ip`/`port`/`unit`.
- В `.sample` — **только подставные** значения (фейковый IP из частного диапазона);
  реальные учётные данные туда не кладут.
- `dds238.json` исключён через `.gitignore` (не коммитить, содержит адреса/учёт).

## Регистры DDS238 (per dds238read.py, read_holding_registers(0, 27))

| Регистр(ы) | Показатель | Формула |
|------------|------------|---------|
| 0-1 | TotalEnergy (общая) | `(regs[0]*65536+regs[1])/100`, kWh |
| 8-9 | ExportEnergy (отдача в сеть) | `(regs[8]*65536+regs[9])/100`, kWh |
| 10-11 | ImportEnergy (потребление из сети) | `(regs[10]*65536+regs[11])/100`, kWh |
| 12 | Напряжение | `regs[12]/10`, V |
| 13 | Ток | `regs[13]/100`, A |
| 14 | Активная мощность (знаковое) | `int16(regs[14])`, W; отрицательное = отдача в сеть |
| 15 | Реактивная мощность (знаковое) | `int16(regs[15])`, var |
| 16 | Коэффициент мощности | `regs[16]/1000` |
| 17 | Частота | `regs[17]/100`, Hz |

Проверено на живом счётчике 192.168.13.77 (2026-09-08): `Import + Export == Total`
(двунаправленный счётчик работает корректно), напряжения/токи/мощности правдоподобны.

## Мгновенные значения (`values`)

Счётчик отдаёт в универсальный контракт теги с приставкой `meter_` (добавлены в
`commonContractTags`):

| Тег | Единица | Источник |
|-----|---------|----------|
| `meter_voltage` | V | reg 12 / 10 |
| `meter_current` | A | reg 13 / 100 |
| `meter_active_power` | W | int16(reg 14); отриц. = отдача в сеть |
| `meter_reactive_power` | var | int16(reg 15) |
| `meter_power_factor` | — | reg 16 / 1000 |
| `meter_frequency` | Hz | reg 17 / 100 |
| `meter_import` | kWh | рег 10-11 (накопительный) |
| `meter_export` | kWh | рег 8-9 (накопительный) |
| `meter_total` | kWh | рег 0-1 (накопительный) |

Эти значения пишутся в Redis (`current` + временной ряд через `SaveSnapshotWindow`,
одна строка за 10 с) и усредняются аккумулятором в `sunreceiver.averages` (5-минутные
агрегаты). Из-за того, что теги `meter_*` не входят в ряды активной мощности инверторов
(`ac_active_power`), счётчик не попадает на графики мощности инверторов и суммарный ряд —
только на собственную плашку/графики.

## Посуточные тарифы

Тарифные зоны (константа в коде): **День 07:00–23:00**, **Ночь 23:00–07:00**
(23:00–24:00 и 00:00–07:00).

Каждую границу (00:00, 07:00, 23:00 локального времени) опрос каждую секунду фиксирует
показание `Import`/`Export`, ближайшее к границе (в пределах окна ±5 с). Значения
пишутся в таблицу `sunreceiver.daily_tariffs`; как только у календарного дня собраны все
4 граничные показания (00:00, 07:00, 23:00 и 00:00 следующего дня), день финализируется:

```
import_day   = Import(23:00) - Import(07:00)
import_night = (Import(07:00) - Import(00:00)) + (Import(00:00 след.дня) - Import(23:00))
export_day   = Export(23:00) - Export(07:00)
export_night = (Export(07:00) - Export(00:00)) + (Export(00:00 след.дня) - Export(23:00))
```

Если какая-то разность отрицательна (счётчик сброшен/заменён) — день не финализируется,
граничные показания сохраняются для диагностики.

### Добор пропущенных границ

Отказоустойчивость: если пулер был выключен / в перезапуске либо не было сети (счётчик молчал),
живой захват границы (±5 с) пропускается — граничное показание не записывается. В этом случае
после возобновления работы фоновый процесс `runMeterBackfill` (запускается при старте и каждые 5 мин):

1. Проходит по границам за окно удержания Redis (последние 2 календарных суток), которые уже
   «безопасно в прошлом» (старше 10 мин — пока живомy захвату дан шанс) и не были захвачены;
2. для каждой пропущенной границы находит в ряде Redis **ближайшее** к ней из зафиксированных
   показаний `Import`/`Export` (поиск в ±6 ч от границы, `nearestMeterReading`);
3. дописывает его в `daily_tariffs` (через `StoreMeterBoundary`, что триггерит финализацию дня).

Если рядом с границей не оказалось ни одного снимка в окне Redis (пулер был выключен дольше
примерно 2 календарных суток) — граница не восстанавливается, день останется без тарифных
значений (best-effort по ТЗ: «ближайшее из зафиксированного»).

### Таблица `sunreceiver.daily_tariffs`

| Колонка | Назначение |
|---------|------------|
| `day` (PK) | Календарный день |
| `import_0000/0700/2300/next`, `export_*` | Граничные показания (kWh) |
| `import_day`, `import_night`, `export_day`, `export_night` | Вычисленные тарифные значения (kWh) |
| `finalized` | Время финализации (непусто = день посчитан) |

Посуточные значения дают основу для статистики за месяц/год и графиков (реализация
дашборда тарифов — отдельная задача).

## Файлы реализации

- `meter_client.go` — Modbus-TCP клиент (holding registers, `[]uint16`, big-endian),
  переиспользуемое соединение.
- `meter_config.go` — чтение `dds238.json`.
- `meter_poller.go` — 1-сек цикл опроса + запись в Redis (`SaveSnapshotWindow`) и вызов
  тарифного захвата.
- `meter_tariff.go` — захват граничных показаний, финализация дня, методы PG
  (`StoreMeterBoundary`, `finalizeMeterDay`, `ensureMeterTariffSchema`).
- `meter_backfill.go` — добор пропущенных границ (`runMeterBackfill`, `nearestMeterReading`).
- `main.go` — загрузка конфига и запуск `runMeterPoll`.
- `pg_store.go` — вызов `ensureMeterTariffSchema` из `ensureSchema`.
