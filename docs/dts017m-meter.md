# Электросчётчик DTS017M (мгновенные значения + посуточные тарифы)

Модуль опрашивает трёхфазный счётчик **DTS017M** (Wenzhou Taiye Electric, серия 7P)
через прозрачный шлюз по **Modbus RTU** и решает две задачи:

1. **Мгновенные значения** (напряжения, токи, мощности, cosφ, частоты, накопленные
   энергии) → в собственные ключи/ряд Redis, затем 5-минутные средние в собственную
   таблицу PostgreSQL.
2. **Посуточные тарифные значения** «День/Ночь» × «потребление из сети / отдача в
   сеть» — считаются **самостоятельно** по границам тарифных зон (историю счётчика
   не читаем).

Логика повторяет модуль [DDS238](dds238-meter.md) (опрос, агрегация, посуточная
статистика), но хранилище **полностью обособлено**: собственные ключи/ряд Redis,
собственные таблицы PG и отдельный аккумулятор. Общие `sunreceiver:current` /
`sunreceiver:series:*` / `averages` / `daily_tariffs` (инверторы, МАП, DDS238) не
используются.

> **Статус:** реализованы пулинг, хранение, агрегация, добор и посуточные тарифы.
> **В дашборде:** рамка «Гараж» с плашками тарифов (главная) и графики «Гараж» на
> странице «Электроэнергия» (`/api/dts017m/current`, `/api/dts017m/tariffs`).
> Дополнительно активная мощность `dts017_active_power` используется на схеме
> анимации как мощность счётчика гаража (`/api/animation`, `garage_meter_power`;
> резервно — CE308, см. [ce308.md](../modules/ce308.md)).

## Источник протокола

Исследование устройства и карта регистров —
`~/src/DTS-DLT645-2007/dts017m-monitoring.md` / `PROTOCOL.md`. Кратко:

- Заявлен DL/T 645-2007, фактически рабочий протокол — **Modbus RTU** (unit 1;
  чтение — функции `03`/`04`, запись — `10`). Историю счётчика (`0x0300+`/`0x0400+`)
  **не пулим**.
- Множитель `Cr` (变比) уже применён счётчиком к току/мощности/энергии; при `Cr=1`
  энергия: `кВт·ч = raw / 100` (Long ×0.01).
- Энергия — Long (2 регистра, старшее слово первым); мощности P/Q — **INT16**
  (знак = направление); токи — модуль.

## Конфигурация

Раздел **`dts017m`** в `sunReceiver.json`. `disabled` — **ОБЯЗАТЕЛЬНОЕ** поле
(отсутствие = ошибка загрузки конфига): `true` — опрос выключен.

```json
{
  "dts017m": {
    "disabled": false,
    "name": "Электросчётчик DTS017M",
    "ip": "192.168.0.41",
    "port": 502,
    "unit": 1,
    "protocol": "rtu",
    "poll_interval": 1
  }
}
```

| Поле | Назначение | По умолчанию |
|------|------------|--------------|
| `disabled` | Обязательное: `true` — опрос выключен | — |
| `name` | Логическое имя (обязательно при активном разделе) | — |
| `ip` | Адрес шлюза/счётчика (обязательно) | — |
| `port` | TCP-порт | 502 |
| `unit` | Modbus-адрес | 1 |
| `protocol` | `"rtu"` (прозрачный шлюз, raw Modbus RTU на TCP) или `"tcp"` (Modbus TCP) | `"rtu"` |
| `poll_interval` | Период опроса, секунды | 1 |

Правила заполнения: реальные адреса — только в приватном `sunReceiver.json`
(`.gitignore`); публичный шаблон `sunReceiver.sample.json` — с подставными значениями.

## Поток данных

```
DTS017M → (Modbus RTU через прозрачный шлюз)
   → dts017 poller (poll_interval)
       → Redis  HASH sunreceiver:dts017m:current            (последний снимок)
                ZSET sunreceiver:dts017m:series:<YYYY-MM>  (каждое показание, окно 2 суток)
       → (границы 00:00/07:00/23:00) захват Import/Export
                → PG sunreceiver.dts017m_daily_tariffs
   → dts017 accumulator (5 мин) → PG sunreceiver.dts017m_averages
```

## Регистры (чтение функцией 03/04)

Телеметрия — блок `0x0000`, `count=29` (`0x00..0x1C`, регистр `0x06` пропущен);
энергии — блок `0x001D`, `count=52` (`0x1D..0x50`). Масштабы:

| Адрес | Данные | Формат |
|---|---|---|
| `0x00..0x02` | Ua/Ub/Uc | UINT ×0.1 В |
| `0x03..0x05` | Ia/Ib/Ic | UINT ×0.01 А |
| `0x07..0x0A` | ΣP/Pa/Pb/Pc | INT16 Вт |
| `0x0B..0x0E` | ΣQ/Qa/Qb/Qc | INT16 вар |
| `0x0F..0x12` | ΣS/Sa/Sb/Sc | UINT ВА |
| `0x13..0x16` | cosφ Σ/A/B/C | UINT ×0.001 |
| `0x17..0x19` | Uab/Ubc/Uca | UINT ×0.1 В |
| `0x1A..0x1C` | Fa/Fb/Fc | UINT ×0.01 Гц |
| `0x001D` | общая активная (Σ) | Long ×0.01 кВт·ч |
| `0x0027` | прямая (import) активная | Long ×0.01 кВт·ч |
| `0x0031` | обратная (export) активная | Long ×0.01 кВт·ч |
| `0x003B` | общая реактивная | Long ×0.01 квар·ч |
| `0x0045` | прямая реактивная | Long ×0.01 квар·ч |
| `0x004F` | обратная реактивная | Long ×0.01 квар·ч |

### Знак активной мощности (проверено 2026-10-05)

`ΣP` (и фазы `Pa/Pb/Pc`) — INT16, знак задаёт направление:
**положительная = потребление (прямое), отрицательная = отдача (обратное)**.
Проверено по истории телеметрии: на одном участке с гаража одновременно сняты
CE308 (эталон знака: «+» = потребление) и DTS017M — в одни и те же секунды
(`2026-10-05 19:27:13…40`) CE308 даёт ≈+138 Вт, DTS017M ≈+135…137 Вт, т.е. знаки и
величина совпадают. Поэтому для формулы гаража в анимации инверсия знака
`dts017_active_power` **не требуется** (см. `freshGarageMeterPower` в
`dashboard.go`).

## Синхронизация времени счётчика

Раз в **30 минут** пулер сверяет часы счётчика с локальным временем опрашивающего
хоста и при расхождении **более 2 секунд** корректирует их (единственная запись в
устройство).

- Чтение: регистр `0x0210`, 3 регистра = 6 байт BCD `ss mm hh DD MM YY` (год — 2
  цифры, `20YY`), функцией `04`:
  ```
  01 04 02 10 00 03 <CRC>
  ```
- Запись (только при расхождении > 2 с): функция `10`, регистр `0x0210`, 3 регистра,
  6 байт BCD (проверено на устройстве — `PROTOCOL.md` §5):
  ```
  01 10 02 10 00 03 06 ss mm hh DD MM YY <CRC>
  ```
- Время последней проверки хранится **в памяти** (переменная цикла опроса); при старте
  обнулено, поэтому **стартовая проверка** выполняется на первом же тике опроса,
  далее — каждые 30 минут.
- BCD разбирается/кодируется вручную с проверкой нибблов и допустимых полей (без
  нормализации `time.Date`); некорректный BCD времени игнорируется с записью в лог.

## Контракт `values` (теги `dts017_*`)

Снимок DTS017M хранится как плоская map тегов `dts017_*` (обособленно от общего
контракта `values` инверторов/МАП/DDS238):

- напряжения: `dts017_voltage_a/_b/_c`, `dts017_voltage_ab/_bc/_ca` (В);
- токи: `dts017_current_a/_b/_c` (А);
- мощности: `dts017_active_power[_a/_b/_c]` (Вт), `dts017_reactive_power[_a/_b/_c]`
  (вар), `dts017_apparent_power[_a/_b/_c]` (ВА);
- `dts017_power_factor[_a/_b/_c]`, `dts017_frequency_a/_b/_c` (Гц);
- энергии (накопительные): `dts017_import`, `dts017_export`, `dts017_total` (кВт·ч),
  `dts017_reactive_total`, `dts017_import_reactive`, `dts017_export_reactive` (квар·ч).

## Хранение

### Redis (обособленные ключи)

- `sunreceiver:dts017m:current` — HASH, поле `dts017m`, значение — JSON снимка;
- `sunreceiver:dts017m:series:<YYYY-MM>` — ZSET (score = Unix-сек., member = JSON
  снимка), пишется каждое показание; окно удержания — 2 календарных суток
  (`PurgeOld`).

### PostgreSQL (обособленные таблицы)

- `sunreceiver.dts017m_averages` (PK `(name, ts)`) — 5-минутные средние. Накопительные
  энергии берутся **последним значением окна** (`dts017CumulativeTags`), остальные теги
  усредняются.
- `sunreceiver.dts017m_daily_tariffs` — посуточные тарифы (структура как у
  `daily_tariffs`, но отдельная таблица).

## Посуточные тарифы (считаем сами)

Зоны (`time.Local`): **День 07:00–23:00**, **Ночь 23:00–24:00 и 00:00–07:00**.
Границы захвата: **00:00, 07:00, 23:00**. Историю счётчика не читаем.

- **Живой захват:** пуллер в окне **±5 с** от ближайшей границы фиксирует показание
  `Import`/`Export` с минимальным отклонением (граница 00:00 принадлежит двум дням —
  пишется одной транзакцией, как у DDS238).
- **Финализация дня** (когда собраны 4 границы, разности неотрицательны):

```
import_day   = Import(23:00) − Import(07:00)
import_night = (Import(07:00) − Import(00:00)) + (Import(00:00 след.дня) − Import(23:00))
export_day   = Export(23:00) − Export(07:00)
export_night = (Export(07:00) − Export(00:00)) + (Export(00:00 след.дня) − Export(23:00))
```

- **Добор** (`runDts017Backfill`): немедленно при старте и раз в 5 мин дофиксирует
  пропущенные границы ближайшим показанием из собственного ряда (±6 ч, принимается
  не дальше 30 мин).

Запрос границ/дней для API (`Dts017BoundaryValues`, `DailyDts017TariffsRange`) уже
реализован, но пока не подключён к дашборду.

## Файлы реализации

- `dts017_config.go` — конфигурация/валидация раздела `dts017m`.
- `dts017.go` — регистры, теги, декодер, накопительные теги.
- `dts017_store.go` — обособленные ключи/ряд Redis.
- `dts017_poller.go` — цикл опроса + запись в Redis + захват границ.
- `dts017_tariff.go` — захват границ, финализация дня, схема/методы PG (`dts017m_daily_tariffs`).
- `dts017_accumulator.go` — 5-минутные средние в `dts017m_averages`.
- `dts017_backfill.go` — добор пропущенных границ.
- `dts017_time.go` — проверка/коррекция часов счётчика (BCD `0x0210`, раз в 30 мин).
- `meter_client.go` — переиспользуемый Modbus RTU/TCP-клиент (поле `Func` — код
  функции чтения, для DTS017M `0x04`; запись `WriteMultipleRegisters`, fn `0x10`).
- `main.go` — загрузка конфига, запуск пулера/аккумулятора/добора; `pg_store.go` —
  создание схем; `redis_store.go` — очистка ряда.

## Восстановление Redis из PG

При полностью пустом Redis (и отсутствии в нём данных BMS/DTS017M) ряд и current
DTS017M восстанавливаются из `sunreceiver.dts017m_averages` за окно
`db.pg_restore_window` (по умолчанию 30 суток, не старше окна удержания Redis 2
суток) — в `restoreRedisFromPG`, как для общего ряда/BMS/EnBMS. Наличие данных
DTS017M в Redis проверяется отдельно (`redisDts017DataPresent`), чтобы не перетереть
сложившийся ряд.
