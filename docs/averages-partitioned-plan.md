# План: партиционированные колоночные таблицы `*_averages_r`

Статус: **выполнено** (2026-10-16). Этапы 1–6 завершены на проде:
`*_averages_r` созданы (помесячные партиции), сервис пишет и читает их,
история мигрирована (`--migrate-avg`, ~3.07M строк, идемпотентно), старые
`*_averages` удалены. Суммарный размер схемы `sunreceiver` — **704 МБ** против
~2 ГБ до рефакторинга. Цель — оптимизировать хранение 5-минутных средних в PG
под профиль «графики» (диапазонный скан по `ts`, много данных за годы).

## Решения
- **Имена:** `<исходная>_r` (суффикс R).
- **Партиционирование:** `PARTITION BY RANGE (ts)`, помесячно; `PK (ключ, ts)` + индекс по `ts`.
- **Колоночная раскладка:** `values jsonb` → типизированные колонки `double precision`
  (инстантанты) ; текстовые метаданные (`base`/`source`/`bms_type`/…) → `text`.
- **BMS (бинарный контракт):** раскладывается **по оригинальному контракту**
  (`internal/bmscontract`): скаляры/метаданные → колонки; массивы
  `cells_v`/`temperatures_c`/`alarm_bytes` → дочерние таблицы
  `bms26_averages_r_cells|_temps|_alarm(name, ts, idx, v)` с тем же партиционированием.
  Агрегация: `avg` для ячеек/температур, `last`/`OR` для битфилдов и байтов
  (усреднять нельзя). **И аккумулятор (этап 2), и миграция (этап 5) используют один
  и тот же оригинальный бинарный контракт `internal/bmscontract`** — без
  самодельного разбора JSON.
- **Авто-создание партиций:** функция `sunreceiver.ensure_month_partition(parent, ts)`.
  BEFORE-триггер на parent **не годится** (PG выполняет tuple routing до BEFORE-ROW-
  триггеров) → партиции обеспечивает **приложение**: при старте и каждые 12 ч держит
  горизонт −1…+2; в этапе 1 предсоздан горизонт **25 мес**.
- **История** остаётся в старых таблицах до этапа 5; новые таблицы — только для
  новой записи (этапы 2–4).
- **PG без FOREIGN KEY** — только индексы. Ссылочная целостность связанной группы
  строк (напр. BMS parent↔`_cells/_temps/_alarm`) обеспечивается **общей
  транзакцией** (общий Commit/Rollback), а не проверками БД: убирает лишние
  проверки при вставке и проблему гонок.
- **Обслуживание партиций:** при старте и каждые 12 ч создаются месяцы −1…+2
  (прошлый — под окно backfill/restore, плюс 2 вперёд — сервис работает месяцами
  без перезапуска).

## Этапы
1. **DDL** (`scripts/step1_averages_partitioned.py`, выполнен): созданы
   `*_averages_r` (+`bms26_averages_r_cells/_temps/_alarm`), функция ensure, горизонт 25 мес.
2. **Код сервиса** (без деплоя):
   - **Писатели:** 5-мин средние пишутся в `*_averages_r` (колоночные insert'ы вместо
     jsonb) — `insertInvAveragedExec` (deye/sofar), `insertDds238AveragedExec`,
     `insertMapAveragedExec`, `insertKesAveragedExec`, `InsertCe308Average`,
     dts017m-писатель; BMS — `bms26Accumulator`/`insertBms26AveragedExec` раскладывают
     по `internal/bmscontract` (parent + `_cells/_temps/_alarm`), агрегация
     avg/last/OR по семантике полей.
   - **Читатели:** после деплоя читают ТОЛЬКО `*_r` (без union со старыми). Сразу
     после деплоя графики показывают лишь новые данные (история ещё в старых) —
     приемлемо; после этапа 5 (миграция) история появляется в `*_r`.
   - **Партиции:** при старте и каждые 12 ч приложение обеспечивает горизонт
     (`ensure_month_partition` на месяцы −1…+2) — держит покрытие без cron/partman.
3. **Ревью** изменений (те же ревьюеры, несколько раундов, до закрытия замечаний).
4. **Деплой + проверка прода 1 мин.** Итог: новая запись — в `*_r`, история — в старых.
5. **Миграция данных** старые→новые ПОСЛЕ деплоя, идемпотентно
   (`ON CONFLICT DO NOTHING` — не затирает уже записанные новые точки);
   BMS — **на Go через `internal/bmscontract`**; проверка (сверка сумм/строк/границ).
6. **Удаление старых таблиц.**

## Критерии проверки
- Размер новых таблиц vs старых (цель — кратное сокращение на сопоставимом объёме).
- `/api/series` за 1/30/365 дней: корректность и p95 времени.
- После этапа 5: старые и новые таблицы дают одинаковые ряды на пересечении периодов.

## В таблицах `*_r` (колонки)
- deye/sofar: `serial (PK), ts, name, device_sn, ip` + 17 метрик.
- dds238/map/kes: `name (PK), ts, device_sn` + 9/7/7 метрик.
- ce308: `name (PK), ts` + 14 метрик.  dts017m: `name (PK), ts, device_sn` + 34 метрики.
- bms26: `name (PK), ts, base, serial, source, bms_type, device_name` + 22 скаляра;
  дети `_cells/_temps/_alarm(name, ts, idx, v)`.
