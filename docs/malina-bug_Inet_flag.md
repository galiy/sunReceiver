# Баг/особенность новой Малины: `_Inet_flag` и инверсия знака сети МАП

> Исследование 2026-09-25, после замены ПАК «Малина». Касается ветки веб-API
> `read_json.php?device=map` (используется, когда в `sunReceiver.json` задано
> `map.rs485.disabled=true`). Modbus-ветка (`mapMAPRegisters`, порт МАП 502) не
> затронута — она всегда берёт знак из `_PNET_Sign_P`.

## 1. Кратко

После замены МАЛИНЫ новая прошивка (`mapd`, `fw=4.3`) стала отдавать
**мощность сети МАП (`_PNET_calc`) без привязки знака к направлению**. Сырой ток
сети `_INET=0x423` — беззнаковая величина («отбираемый от сети»), а `mapd` лишь
опционально инвертирует знак по своему полю `_Inet_flag`. Флаг **динамический**
(переключается во времени, встречается и `0`, и `1` при одном и том же направлении)
и **не определяет направление** — поэтому по нему нельзя восстановить, потребление
это или отдача.

Авторитетный знак направления — сырая ячейка `_PNET_Sign_P=0x587`:
`1` — потребление из сети, `0` — отдача/продажа. Именно её использует
Modbus-ветка (`mapMAPRegisters`). В JSON `read_json.php?device=map` эта ячейка
отсутствует, поэтому читается отдельно через `read_memory.php?offset=1415&count=1`.

Историческая заметка: первая версия разбора ошибочно трактовала `_Inet_flag` как
«признак инверсии знака относительно контракта» — при заряде это случайно совпадало,
но при отдаче в сеть формула давала неверный знак (см. §3.1).

## 2. Симптом

Во время ежедневного заряда АКБ из сети дашборд стал показывать «отдачу в сеть»:
`grid_power` МАП отрицательный, хотя электросчётчик DDS238 показывает импорт
(положительный). Совпало с заменой Малины 24.09.2026 (окно 18:16–21:40 MSK,
данные МАП пропадали).

## 3. Сравнение с сырьём (главное)

### 3.1. Потребление (заряд АКБ), 25.09.2026 ~00:29 MSK (`_MODE=4`)

| Источник | Значение | Комментарий |
|---|---|---|
| Сырой `0x423` (`_INET`) | **+78** | «Ток отбираемый от сети», величина |
| Сырой `0x587` (`_PNET_Sign_P`) | **1** | 1 = положительная мощность (потребление) |
| API `_UNET` | 213…217 | напряжение сети, В |
| API `_INET` | **−78** | mapd инвертировал знак (`_Inet_flag=1`) |
| API `_PNET_calc` | **−13578.8 … −13833.8** | |_UNET × _INET|, знак от mapd |
| API `_Inet_flag` | **1** | флаг инверсии mapd |
| Электросчётчик `meter_active_power` | **+15953 … +16592** | импорт (потребление, «+») |

Позже (25.09.2026 ~01:04:48 MSK, потребление продолжается, сырой `0x587=1`) флаг
вернулся в `0`:

| `_Inet_flag` | API `_INET` | API `_PNET_calc` | Сырой `0x587` | Направление |
|---|---|---|---|---|
| `1` | −78 | −13833.8 | 1 | потребление |
| `0` | +77 | +13770.0 | 1 | потребление |
| отсутствует (старая прошивка) | +5 (пример) | +1141.2 (пример) | 1 | потребление |

Напрашивался вывод «`_Inet_flag=1` ⇒ API инвертирует знак» (и правило
`grid_power = (_Inet_flag != 0) ? −_PNET_calc : _PNET_calc`). Но он **ошибочен** —
см. §3.2.

### 3.2. Отдача в сеть, 25.09.2026 ~09:01 MSK (`_MODE=17`), три замера подряд

| `_Inet_flag` | API `_INET` | API `_PNET_calc` | Сырой `0x587` | Факт (счётчик/режим) |
|---|---|---|---|---|
| `1` | −17 | −3735.2 | **0** | отдача в сеть |
| `0` | +16 | +3512.2 | **0** | отдача в сеть |
| `0` | +17 | +3808.0 | **0** | отдача в сеть |

Все три замера — одна и та же физическая отдача (`0x587=0`), но `_Inet_flag`
переключается `1 → 0 → 0` между опросами. Формула по флагу даёт:
+3735 (при `flag=1`) и +3512/+3808 (при `flag=0`) — **все три положительные, т.е.
ложное «потребление»**. Значит `_Inet_flag` **не кодирует направление** и не может
быть основой знака.

### 3.3. Верное правило

Направление берётся из сырого `_PNET_Sign_P` (0x587), мощность — по модулю
`_PNET_calc` (контракт дашборда: потребление `+`, отдача `−`):

```
grid_power = (0x587 == 1) ? +|_PNET_calc| : −|_PNET_calc|
```

Это ровно та семантика, что уже реализована в Modbus-ветке
(`mapMAPRegisters`, `main.go`).

## 4. Сопоставление со старым источником и счётчиком

Непрерывный ряд `sunreceiver:series` (Redis), устройство МАП `192.168.13.74`
против счётчика `192.168.13.77`:

| Период | Совпадение знака с счётчиком |
|---|---|
| 20.09–24.09 (старая Малина) | 1081 из 1081 |
| с 24.09 ~20:00 (новая Малина) | 499 из 500 — **противоположны** |

В момент заряда до замены: MAP `grid_power ≈ +6…+7 кВт`, счётчик `+6.9…+8.3 кВт`
(совпадает). После замены: MAP `≈ −8…−13.8 кВт`, счётчик `+10.9…+16.5 кВт`
(противоположно). Даже на холостом ходу (сеть: MAP `−0.65 кВт`, счётчик `+0.75 кВт`)
знак был перевёрнут. Причина — не «глобальная инверсия», а то, что знак `_PNET_calc`
у новой прошивки вообще не связан с направлением: он определялся случайным состоянием
`_Inet_flag`, а не `0x587`. Поэтому в одних режимах/моментах совпадало, в других — нет.

## 5. Что такое `_Inet_flag`

- В протоколе МАП (`docs/map/map/protocol_MAP_cells_2026_07_15.doc`) **нет** ячейки
  `_Inet_flag`. Там документированы только:
  - `_UNET=0x422` — напряжение сети (`U = UNET+100`);
  - `_INET=0x423` — ток, отбираемый от сети (без знака);
  - `_INET_16_4=0x431` — более точный ток сети;
  - `_PNET_Sign_P=0x587` — **знак мощности сети**: `1` положительная (потребление),
    `0` отрицательная (продажа);
  - `_PNET_8=0x59A-0x59B` — мощность сети, знак по `0x587`.
- Значит `_Inet_flag` — поле/состояние **ПО ПАК «Малина»** (`mapd`), которым оно
  чисто косметически меняет знак тока/мощности сети в `read_json.php`. Направление
  (потребление/отдача) оно **не несёт**: в §3.2 при одной и той же отдаче флаг
  переключается между 0 и 1. Почему у нового `mapd` (`fw=4.3`) он так себя ведёт —
  по внешним данным не определить; на направление это не влияет.
- Направление всегда берётся из `_PNET_Sign_P=0x587`: `1` — потребление,
  `0` — отдача. В `read_json.php` этой ячейки нет, читается через `read_memory.php`.
- В старом сэмпле Малины (`docs/read_json.md`, 2026-09-07) `_Inet_flag=0`; тогда
  знак `_PNET_calc` совпадал с направлением (прошивка `fw=3.7`), поэтому баг не
  проявлялся.
- SSH на новую Малину закрыт (порт 22 `Connection refused`), исходники `mapd`
  недоступны; веб-интерфейс отдаёт только `read_json.php`/`read_memory.php`.

## 6. Влияние на sunReceiver и правка

Затронута только ветка веб-API (`mapMAPAPI`, `mppt_api.go`):

- `grid_power` брался напрямую из `_PNET_calc`, поэтому уезжал в Redis/PG со знаком,
  не отражающим направление → на графике/плашке «Мощность сети» и в потоках анимации
  Дома рисовалась отдача вместо потребления (и наоборот — при отдаче теперь `+`).
- `battery_power` (`−_PLoad_calc`), `grid_voltage` (`_UNET`), ток АКБ и температуры
  были корректны.

Итоговая правка: направление берётся из сырой ячейки `_PNET_Sign_P` (0x587),
мощность — по модулю `_PNET_calc`. Ячейка читается отдельным запросом
`mpptSite.FetchPNETSign` (`read_memory.php?offset=1415&count=1`) раз в цикл опроса
МАП; результат кладётся в `mapRaw.PNETSign`:

```go
if v, ok = parseFloat(r.PNetCalc); ok {
    if r.PNETSign != nil {              // 0x587 прочитан
        if v < 0 { v = -v }             // модуль
        if *r.PNETSign == 0 { v = -v }  // 0 — отдача в сеть
    } else if invertGridFromInetFlag(r.InetFlag) {
        v = -v                          // фолбэк: недоступна 0x587
    }
    out["grid_power"] = v
}
```

Modbus-ветка (`mapMAPRegisters`) не изменялась — там знак и так берётся из
`_PNET_Sign_P`. Тесты: `TestMapMAPAPIGridPowerRawSign` (0x587=1/0 при разных
`_Inet_flag` и при отсутствии ячейки), `TestMapMAPAPIGridPowerSign` (фолбэк по
`_Inet_flag`), `TestMapMAPAPIParse`.

> Ранее (§ до правки) знак брался условно по `_Inet_flag` — коммит `a909624`.
> При заряде это совпадало случайно, при отдаче (`fw=4.3`) — нет (§3.2).

Дополнительно (для точности формулы «Мощность дома») введена подстановка счётчика
DDS238: `P(сеть)` = `meter_active_power`, если ближайший снимок не старше
`meterGridMaxAge=20 с`, иначе `grid_power` МАП. Применяется в `/api/current`
(плашка «Мощность дома»), `/api/animation` (поля `house_grid_power`, рёбра
«МАП → Сеть дома» и «Сеть дома → Дом») и `/api/series` (ряд `house_power`).

> История правок: `d90c603` — безусловная инверсия (устарела); `a909624` — условная
> инверсия по `_Inet_flag` (устарела, при отдаче в сеть давала неверный знак);
> текущая — по сырой `0x587`.

## 8. Как проверить/диагностировать

Сырьё и API новой Малины (`admin` / пароль из раздела `map` конфига):

```sh
curl -s -u admin:PASS "http://192.168.13.60/read_json.php?device=map" \
  | python3 -c 'import sys,json;o=json.load(sys.stdin);print(o["_Inet_flag"],o["_INET"],o["_PNET_calc"])'

# сырой знак мощности сети (0x587=1415, 0x423=1059)
curl -s -u admin:PASS "http://192.168.13.60/read_memory.php?offset=1415&count=1"
curl -s -u admin:PASS "http://192.168.13.60/read_memory.php?offset=1059&count=1"
```

Критерий корректности на стороне sunReceiver: знак `grid_power` МАП должен совпадать
со знаком `meter_active_power` счётчика DDS238 (при отсутствии генерации ночью — точно).

## 9. Открытые вопросы и рекомендации

- Точное определение `_Inet_flag` в прошивке `mapd` не найдено (нет документации,
  SSH закрыт). Для направления он бесполезен (§3.2); оставлен только фолбэком на
  случай недоступности `read_memory.php`.
- Реализован «железобетонный» вариант: модуль `|_PNET_calc|` + знак из сырого
  `_PNET_Sign_P=0x587` (`read_memory.php?offset=1415&count=1`). Цена — лишний
  HTTP-запрос на каждый опрос МАП (~1/с), тот же хост/Basic-auth, что и MPPT.
- Если после обновления `mapd` изменится адрес/семантика `0x587` — перепроверить
  `0x587` и знак счётчика; при ошибке `FetchPNETSign` автоматически включится
  фолбэк по `_Inet_flag` (в лог пишется предупреждение).
