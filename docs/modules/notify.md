# Уведомления в MAX (`notify.go` + `cmd/maxbot`)

Отправка событий мониторинга в мессенджер **MAX** через Bot API
(`platform-api2.max.ru`). Отслеживается только МАП Титанатор (батарея/сеть) — за
его недоступностью и напряжением сети; сообщения уходят при аварии и при
восстановлении.

Архитектура разделена на два процесса:

- **sunReceiver** (`notify.go`) — мониторинг МАП, детекция событий с гистерезисом
  и дедупликацией, формирование готового текста, запись события в Redis Stream.
- **maxbot** (`cmd/maxbot`) — отдельное приложение: читает тот же Stream,
  отправляет текст в MAX через Bot API и после успешной отправки подтверждает
  запись (XACK) — сообщение удаляется из Redis. Также сопровождает подписку бота
  (регистрирует первого подписчика и сохраняет адресат в собственный конфиг).

## Принцип работы

1. **sunReceiver: детекция.** `mapTrack` — потокобезопасный трекер состояния МАП,
   заполняется `pollMAPMalina26` (API «Малина26»): последний успешный/неудачный
   опрос, причина ошибки и timestamp ответа API. `runNotifyMonitor` — фоновый цикл
   (каждые `notifyPollEvery` = 5 с), оценивающий состояние МАП и через два
   `alertDetector` (недоступность / напряжение) формирующий сообщения.
2. **sunReceiver: запись в Stream.** Сформированное пограничное сообщение
   записывается в Redis Stream `sunreceiver:notify:events` (поля `type="map"`,
   `text`, `ts=RFC3339`). Подтверждение у детектора (`confirmDispatched`) ставится
   **после успешной записи в Stream** — то есть событие попадает в очередь ровно
   один раз (при сбое Redis оно остаётся в outbox и ретраится).
3. **maxbot: отправка.** Читает Stream (consumer group `maxbot`, XREADGROUP),
   отправляет `text` в `POST https://platform-api2.max.ru/messages` с заголовком
   `Authorization: <token>`. После ответа `200` — подтверждает (XACK) и удаляет
   запись (XDEL). Адресат — `user_id` (личный диалог) или `chat_id` (чат/канал).

> Подтверждение отправки/доставки: ответ `200` с объектом `message` (`mid`).
> `401` — неверный токен, `403` — нет доступа к получателю, `429` — лимит.
> Лимит API — 2 сообщения/сек на чат, 30 rps.

## Какие события отслеживаются (детекция осталась в sunReceiver)

### 1. МАП недоступен
Конкретизируется причина в тексте сообщения:
- **`stale`** — веб-API ПАК «Малина» отдаёт сильно устаревшее время (поле
  `timestamp` ответа API «Малина26»), и оно **не изменяется**
  (зависший API);
- **`down`** — нет валидных данных дольше окна `map_undeclared`:
  - при источнике «веб-API» — недоступно/не отдаёт данные МАП (ошибка запроса);
  - при источнике «RS232/Modbus» — опрос не удался (нет данных от МАП).

### 2. Напряжение сети МАП отсутствует/ниже порога
Порог `grid_voltage_low` (по умолчанию **195 В**). Считается по напряжению сети
МАП (`grid_voltage`): если тега нет либо значение `< порога` либо `<= 0`.
Если опрашивается электросчётчик (раздел `meter`), в сообщение добавляется
справочное напряжение счётчика (`meter_voltage`).

> **Свежесть счётчика.** Если счётчик опрашивается (раздел `meter`), в сообщение
> добавляется его состояние:
> - **свежий снимок** (< `meterFreshWindow`) — «Напряжение счётчика: N В»;
> - **счётчик молчит** (снэпшот устарел) — «Счётчик недоступен (последний снэпшот:
>   YYYY-MM-DD HH:MM:SS)» (время последнего успешного считывания).
>
> Если счётчик обесточен (нет напряжения сети), он перестаёт отвечать, и в `current`
> остаётся последний успешно снятый снимок со старым timestamp — тогда напряжение
> **не** показывается как живое (это создавало бы ложную картину «напряжение есть»),
> а выводится признак недоступности с датой последнего снэпшота.

### 3. Восстановление
По обоим событиям отправляется отдельное сообщение, когда состояние вернулось в
норму и продержалось окно стабильности.

## Гистерезис и стабильность

- **Авария** фиксируется после непрерывного удержания условия в течение
  `stable_window` (по умолчанию **30 с**).
- **Восстановление** — аналогично: состояние держится в норме `stable_window`,
  и только потом шлётся сообщение.
- **Дедупликация**: `alertDetector` формирует сообщение один раз на переход, не
  повторяясь, пока состояние не сменится.
- Пока МАП недоступен, оценка напряжения приостанавливается (детектор
  сбрасывается) — аварию напряжения обработает ветка недоступности.

## Очередь (Redis Stream) и дедупликация

- Ключ потока: `sunreceiver:notify:events`; солнцеприёмник пишет XADD с `MAXLEN ~
  1000` (приблизительный — защита от бесконечного накопления).
- Запись: JSON-поля `type="map"`, `text`, `ts` (RFC3339).
- **Дедупликация в sunReceiver**: событие попадает в очередь один раз — детектор
  сбрасывает `pending` только после успешной записи в Stream. Если запись не
  удалась, событие остаётся в outbox и повторяется на следующем такте.
- **Накопление при отсутствии адресата**: maxbot не отправляет и не подтверждает
  события, пока адресат не зарегистрирован (нет `user_id`/`chat_id`). Они
  остаются в очереди и уходят после регистрации подписчика. Их немного благодаря
  дедупликации и гистерезису.
- **Подтверждение («удаление после успешной отправки»)**: maxbot подтверждает
  запись XACK и удаляет XDEL только после ответа `200` от MAX. При неудаче
  отправки запись остаётся в очереди и ретраится.
- **Незавершённые (pending)**: maxbot при старте переназначает зависшие у других
  консьюмеров записи (XAUTOCLAIM), а также периодически дособирает незавершённые
  своего консьюмера (XREADGROUP со сдвигом `0`), чтобы после появления адресата
  или рестарта доставить накопленные события.
- **Редкий дубль**: при крахе maxbot между отправкой в MAX и XACK событие может
  быть отправлено повторно. Для уведомлений допустимо.

## Условие включения

Мониторинг в sunReceiver запускается **только если включён опрос МАП в целом**: есть
источник МАП (API «Малина26» — `malina26`) и `map.disabled=false`.
Если опрос МАП выключен (`map.disabled=true` или нет источника), уведомления **не**
формируются, даже при настроенном разделе `notify`.
maxbot независим от опроса МАП: он всегда читает очередь и отправляет то, что в
ней есть (пока адресат не зарегистрирован — копит).

## Конфигурация sunReceiver (`sunReceiver.json` → `notify`)

```json
"notify": {
  "disabled": false,
  "stable_window_sec": 30,
  "map_undeclared_sec": 20,
  "grid_voltage_low": 195
}
```

| Поле | Обязательность | Описание |
|---|---|---|
| `disabled` | опц. | `true` — мониторинг МАП и запись событий в Stream выключены |
| `stable_window_sec` | опц. | окно стабильности (дефолт 30) |
| `map_undeclared_sec` | опц. | окно недоступности МАП (дефолт 20) |
| `grid_voltage_low` | опц. | порог напряжения сети МАП, В (дефолт 195) |

> **Токен/адресат здесь больше НЕ настраиваются.** Они переехали в приложение
> `maxbot` (см. ниже). В sunReceiver остаются только пороги детекции и признак
> включения мониторинга.

## Конфигурация maxbot (`maxbot.json`, приватный, `/opt/maxbot/`)

```json
{
  "token": "CHANGE_ME",
  "user_id": "",
  "chat_id": "",
  "disabled": false,
  "redis": "host:port",
  "consumer": "maxbot"
}
```

| Поле | Обязательность | Описание |
|---|---|---|
| `token` | обязателен | токен бота MAX (в открытом виде, файл в git не выгружается) |
| `user_id` | необязат. | адресат — личный диалог; **заполнять не нужно** (см. ниже) |
| `chat_id` | необязат. | адресат — чат/канал; **заполнять не нужно** (см. ниже) |
| `disabled` | опц. | `true` — бот не запускается (раздел есть, но без отправки) |
| `redis` | обязателен | адрес Redis sunreceiver (host:port или unix-сокет), откуда читать Stream |
| `consumer` | опц. | имя консьюмера в consumer group (дефолт `maxbot`); фиксированное имя позволяет дочитать незавершённые после рестарта |

> **`user_id`/`chat_id` заполнять не нужно.** Если они пустые, maxbot автоматически
> регистрирует **первого подписчика** (см. «Автоматическая регистрация адресата»)
> и дописывает его ID в **этот же файл** `maxbot.json`.

## Автоматическая регистрация адресата (в maxbot)

Если `user_id`/`chat_id` пустые, бот сам узнаёт, кому отправлять:

1. **Источник** — long polling `GET /updates` (те же права, что у отправки; в фоне).
   Отслеживаются события подписки/отписки:
   - `bot_started`, `bot_added` — подписка;
   - `bot_stopped`, `bot_removed`, `dialog_removed` — отписка;
   - `message_created` — пользователь написал боту (используется как подписка,
     если адресат ещё не зафиксирован — случай «события есть, а подписчика нет»).
2. **Первый подписчик** становится адресатом: из события берутся `user.user_id` и
   `chat_id`, записываются в `maxbot.json`, и бот приветствует его:
   «Вы зарегистрированы и будете получать сообщения…».
3. **Последующие подписки игнорируются**: адресат не перезаписывается, а автору
   отправляется отказ «Регистрация невозможна: подписка уже привязана к другому
   пользователю».
4. **Отписка текущего подписчика** (`bot_stopped`/`bot_removed`/`dialog_removed` от
   него) очищает `user_id`/`chat_id` в конфиге и возвращает бот в режим ожидания
   нового подписчика.

Адресат хранится **в самом конфиге** `maxbot.json` (не в Redis/PG): он переживает
перезапуски и персистентен.

## Запуск и эксплуатация

- **Прод**: `/opt/maxbot/` — бинарник `maxbot` + `maxbot.json` (приватный),
  systemd-юнит `maxbot.service` (непривилегированный пользователь, выгрузка из
  ФС не требуется — только исходящие TCP).
- Сборка: `make maxbot-linux-x64` → `dist/maxbot-linux-amd64-<version>`.
- **Порядок выката**: сначала развернуть maxbot (с его конфигом), затем убрать
  `token`/`user_id`/`chat_id` из раздела `notify` `sunReceiver.json` и обновить
  бинарник sunReceiver.
- Пока адресат не зарегистрирован, события копятся в Redis и отправляются после
  регистрации (см. «Очередь»).

## Заведение учётной записи, создание бота и подписка (пошагово)

### 1. Учётная запись платформы MAX
Ботов можно создавать только на **платформе MAX для партнёров** — нужен
**верифицированный профиль организации, ИП или самозанятого (резидента РФ)**.
- Платформа: <https://business.max.ru/self> — регистрация и верификация профиля
  (юрлицо/ИП/самозанятый). Для частного использования подойдёт «самозанятый»
  (максимум **2 бота** на профиль).

### 2. Создание бота
- Платформа → **Чат-боты** → **Создать**. Заполнить логотип (500×500, ≤5 МБ, jpg/png),
  название (1–59 символов) и описание (≤200 символов).
- Никнейм генерируется автоматически (публичная ссылка): `idИНН_bot` (ИП/юрлицо)
  или `se(orgid)_bot` (самозанятый) → `max.ru/<ник>`.
- Дождаться **модерации** (обычно до 48 ч по рабочим дням; уведомление приходит от
  бота **MAX для бизнеса**). После успеха — статус **«Опубликован»**.

### 3. Получение токена
- Платформа → **Чат-боты** → бот → **⋮** → **Настройки** → значок копирования у
  поля **Токен доступа**.
- Либо через бота **«MAX для бизнеса»** → команда **«Получить токен»**.
- Токен вписывается в `maxbot.token` (секрет; в git не попадает).

### 4. Подписка на бота
- Адресат открывает диалог с ботом: `max.ru/<ник>` (или находит по нику в поиске).
- Бот получает `bot_started` (при подписке) или `message_created` (при написании)
  и **автоматически фиксирует его как адресата** — отдельно больше ничего настраивать
  не нужно.

## Зависимости от TLS

Cert-цепочка `platform-api2.max.ru` подписана **Russian Trusted Sub CA** → корнем
**Russian Trusted Root CA** (Минцифры). На сервере должен быть установлен корневой
сертификат Минцифры в системный пул (`/usr/local/share/ca-certificates/` +
`update-ca-certificates`), иначе `Verify return code: 20` / `curl` без `-k` не пройдёт.
