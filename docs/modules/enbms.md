# Модуль EnBMS — мониторинг BMS Enjie (EMU110x) по BLE

Опрашивает BMS производства **Shanghai Enjie / N ENERGY** (бренд **EN BMS**;
модели EMU1101/1102/1103, 8S–16S LFP/NCM) по **Bluetooth Low Energy**. Читается
только блок **Battery** (CID2 `0x61`).

- Реализация: `enBms.go`, `enBms_client.go`, `enBms_poller.go`,
  `enBms_accumulator.go`, `enBms_store.go`.
- Протокол и живой срез: `/home/sasha/src/energybms` (`PROTOCOL.md`,
  `DEVICE_SNAPSHOT.md`).

## Конфигурация

Раздел **`enBms`** `sunReceiver.json`:

```json
"enBms": {
  "disabled": false,
  "devices": [
    { "name": "BMS EnBMS #1", "mac": "AA:BB:CC:11:22:33", "disabled": false }
  ]
}
```

- `disabled` (общий) — **обязательное** поле: `true` отключает опрос EnBMS целиком.
- `devices` — коллекция устройств. Каждый элемент: обязательный `disabled`;
  `mac` (обязателен для активного — BLE-подключение идёт по адресу) и/или
  необязательный `name` — произвольная метка для отображения.
- Отсутствие `disabled` у устройства — ошибка загрузки конфига.
- **BLE-имя не используется.** У всех EnBMS заводское имя одинаковое (`BP00`),
  поэтому оно не читается и не является идентификатором. Уникален только MAC:
  он — ключ устройства (Redis/PG), а отображаемое имя = `<name> <MAC>`
  (если `name` пуст — `BMS <MAC>`). `name` задавайте уникальным, но даже при
  одинаковых метках записи различимы и сортируются по MAC.

## Транспорт BLE и протокол

| Роль | UUID |
|---|---|
| Сервис | `0000ff00-…` |
| Запись команд (host→BMS) | `0000ff02-…` |
| Уведомления/ответы (BMS→host) | `0000ff01-…` |

Кадр (big-endian), CRC-16/CCITT (полином `0x1021`, init 0) по `frame[1:len-3]`:

```
Запрос: 7E 10 ADR 46 CID2 LEN(2) INFO CHKSUM(2) 0D            (INFO с 7)
Ответ:  7E 14 ADR CID2 RTN LEN(2) INFO CHKSUM(2) 0D           (INFO с 7)
```

Полная длина = `10 + LENID` (`LENID = frame[5]<<8 | frame[6]`), CRC — по
`frame[1:len-3]`. Сборка — **строго по длине**, а не по `0x0D`: байт `0x0D`
встречается внутри payload. Ответ приходит несколькими notify-фрагментами —
склеиваются в буфере.

> Формат подтверждён живыми кадрами Battery/BasicInfo (CRC-16/CCITT). В
> `DEVICE_SNAPSHOT.md` полные кадры приведены без байта `RTN` — ориентироваться
> на живые (в тестах модуля зафиксирован реальный кадр).

Запрос Battery: `7E 10 00 46 61 00 01 00 <crc> 0D`.

### Payload Battery (106 Б)

`dataflag(u8) slaveNo(u8) batterynum(u8) cells[batterynum×u16, мВ] tempnum(u8)
temps[tempnum×u16, 0.1 K] current(s16, 0.01 А) totalV(u16, 0.01 В)
remaining(u16, 0.01 А·ч) customerp(u8) totalCap(u16, 0.01 А·ч) soc(u16, 0.1 %)
ratedCap(u16, 0.01 А·ч) cycles(u16) soh(u16, 0.1 %) portV(u16, 0.01 В) warnings…`

Мощность протоколом отдельно не отдаётся — считается `P = totalV × current`.

**Знак тока/мощности.** В протоколе EnBMS поле `chargecurrent` (`s16`) имеет
семантику «минус = разряд». В проекте принято обратное соглашение — **разряд
положительный, заряд отрицательный** (как у ANT BMS), поэтому знак тока
инвертируется при разборе; мощность (`U·I`) наследует правильный знак.

## Принципы работы (по образцу CE308 и ANT BMS)

- **Соединение постоянное**: пулер держит BLE-соединение с каждым устройством и
  не рвёт его между опросами; при обрыве переподключается с ограниченным
  бэкоффом (2…30 с). Транзиентный таймаут чтения ретраится (до 3 попыток) без
  разрыва связи; после 3 подряд неудачных опросов соединение переустанавливается.
- **Последовательный опрос**: устройства опрашиваются по одному; общий цикл — не
  чаще `poll.enbms` секунд (обязательный раздел `poll`, по умолчанию 3 с; если
  суммарное чтение дольше — паузы нет).
- **Устойчивость BLE**: переиспользуются хелперы CE308 — управление питанием
  адаптера и перенацеливание tinygo на реальный `hciN`, сброс «залипшего»
  состояния BlueZ, discovery, если устройство не известно BlueZ.
- **Лимит BT-устройств**: суммарное число BLE-устройств (EnBMS + CE308) не должно
  превышать `enbmsMaxBTDevices` (5); иначе опрос EnBMS не запускается, в лог
  пишется ошибка.

## Хранение и усреднение

Схема — как у ANT BMS:

- Redis `sunreceiver:enbms:current` (HASH, поле = MAC) — текущий снимок;
- Redis `sunreceiver:enbms:series:<YYYY-MM>` (ZSET) — **каждое снятое показание**
  (score = секунда, `samples=1`; окно 2 суток, чистка PurgeOld);
- PostgreSQL `sunreceiver.enbms_averages` (`name`=MAC, `ts`, `values` jsonb) —
  вся история с гранулярностью **1 запись / 5 минут**; вставка с sample-count guard;
- неполный 5-минутный промежуток при остановке в PG не пишется (только полные
  бакеты); в Redis он не нужен — сырые показания уже записаны.

При полностью пустом Redis ряд `enbms:series` восстанавливается из PG
(`EnBmsAveragesAll`) — восстановленный участок представлен 5-минутными средними
(`samples>1`), до первых новых опросов ряд смешанный.

Мгновенные поля (ток/мощность/SOC/ёмкости/напряжения ячеек/температуры)
усредняются за 5 минут; дискретные (число ячеек, циклы) берутся по последнему
снимку. Ряд на дашборде прореживается `downsampleBMSSeries` (порог + усреднение),
как и остальные графики.

## Дашборд

EnBMS выводится на дашборд тем же API, что и ANT BMS, — с приведением к форме
`bmsDevice`/`bmsSeriesPoint` и полем `kind="enbms"`:

- `/api/bms` — «батарейки» на главной (блок `BMS (батареи)` включается, если
  настроен ANT BMS или EnBMS; сортировка — по отображаемому имени);
- `/api/bms/<MAC>` и `/api/bms/<MAC>/series` — страница деталей `/bms/<MAC>`
  (карточки, ячейки, температуры, графики: свежая часть — сырые точки из Redis,
  старая — 5-мин средние из PG, ряд прореживается на стороне API).

Отображаемое имя EnBMS — `<name> <MAC>` (BLE-имя не уникально; MAC виден под
батарейкой на главной и в заголовке страницы `/bms/<MAC>`).

Чего в блоке Battery нет (состояния мощностных ключей/балансировки, счётчик
кадров), фронт скрывает по `kind`; отсутствующие у EnBMS поля остаются нулевыми.

## Сигнальный хвост Battery: аварии и балансировка (2026-10-01)

Отдельный CID2 0x44 (`TeleState`) на устройстве недоступен, но предупреждения
приложение получает из **хвоста блока Battery (0x61)**. Раскладка восстановлена из
APK (`parseBody_Battery`, `BmsMsgUtil.dart` `0x3f3a18`; порядок имён — `toJson`
`0x3def6c`): хвост = **39 байт** после телеметрии (INFO=106 Б, телеметрия=67 Б).

| Смещение в хвосте | Байт | Смысл |
|---|---|---|
| 0–15 | 16 (`batterynum`) | warn-список по ячейкам |
| 16–19 | 4 (`tempnum−2`) | warn-список по температурам |
| 20 | 1 | `envtempwarn` |
| 21 | 1 | `powertempwarn` |
| 22 | 1 | `chargecurrentwarn` |
| 23 | 1 | `customerwarnp` |
| 24…38 | — | статусы (`eventwarnlist`, ключи, балансировка, `sysstate`, `brokenstatelist`) |

**Ключевое:** warn-область (смещения 0…23) на здоровом кадре **нулевая**; ненулевые
байты `01 03 08` (смещения 25…27) — это **статусы** (ключ/балансировка/режим), а не
аварии. Декодер (`parseEnBmsTail`) читает аварии только из warn-области, поэтому
ложных плашек нет.

> ⚠️ Ошибочный путь (отвергнут): декодировать аварии из `Ext_Bit`
> XML `teleSignal_Group` (смещение tail[24:38]) — этот XML описывает протокол ПО
> «Upper Computer» (CID2 0x42/0x44), а не Battery (0x61), и даёт ложные срабатывания.
> Статусы (ключи/баланс/режим) пока не декодируются — их смещения не подтверждены.
> Подробный реверс — `energybms/PROTOCOL.md` §5.1.1 и `REVERSE_ENGINEERING.md` §2.1.

### Сырой лог Battery (калибровка)

Пулер пишет payload Battery (hex) в журнал (`enbms: RAW ...`) с таймстампом снятия:
при **изменении** сигнального хвоста и не реже одного раза в 60 с
(`enbmsRawLogInterval`). На Windows журнал — файл `sunReceiver.log` рядом с
бинарником; на Linux — journald. Формат строки:

```
enbms: RAW <name> (<mac>) ts=<RFC3339> tail=<hex 39Б> payload=<hex INFO>
```

Warn-область даёт корректный результат (на здоровом кадре пусто). Запись алармов
EnBMS в `device_errors` (device=`MAC`, kind=`enbms`) пока оставлена **отключённой**
(`enbmsAlarmHistory=false`) — включим после наблюдения первого реального warn-кадра.
Телеметрию алармы не затрагивают.
