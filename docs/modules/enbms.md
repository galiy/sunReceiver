# Модуль EnBMS — мониторинг BMS Enjie (EMU110x) по BLE и RS485

Опрашивает BMS производства **Shanghai Enjie / N ENERGY** (бренд **EN BMS**;
модели EMU1101/1102/1103, 8S–16S LFP/NCM) по **Bluetooth Low Energy** (BLE) либо
по **RS485** (ASCII PACE через прозрачный IP-шлюз или COM-порт). Читается только
телеметрия: BLE — блок **Battery** (CID2 `0x61`), RS485 — **TeleMeter**
(CID2 `0x42`); раскладка телеметрии у них совпадает.

- Реализация: `enBms.go`, `enBms_client.go` (BLE), `enBms_rs485.go` (PACE),
  `enBms_poller.go`, `enBms_accumulator.go`, `enBms_store.go`.
- Протокол и живой срез: `/home/sasha/src/energybms` (`protocol-BLE.md`,
  `protocol-485.md`, `DEVICE_SNAPSHOT.md`).

## Конфигурация

Раздел **`enBms`** `sunReceiver.json`: метод задаётся у КАЖДОГО устройства, период
— для каждого метода. Поэтому в одной коллекции могут быть и BLE-, и RS485-устройства
(они опрашиваются независимыми циклами со своими периодами). Примеры по каждому
транспорту — ниже.

**Поля раздела:**

- `disabled` (общий) — **обязательное** поле: `true` отключает опрос EnBMS целиком.
- `poll_interval_ble` / `poll_interval_rs485` — периоды циклов для каждого метода
  (секунды, > 0; sample: BLE 3, RS485 1). Циклы независимы: BLE-устройства
  опрашиваются с `poll_interval_ble`, RS485-устройства — с `poll_interval_rs485`.
- `devices` — коллекция устройств. Каждый элемент:
  - `disabled` — **обязательное** поле (отсутствие = ошибка конфига);
  - `method` — **обязательное** поле: `"ble"` или `"rs485"`;
  - `mac` (обязателен для `method=ble` — подключение идёт по адресу) и/или
    необязательный `name`. **Ключ хранилища** — MAC (если задан), иначе `name`:
    это позволяет при смене метода (BLE ↔ RS485) сохранять прежний ряд устройства
    (указывайте тот же MAC);
  - `rs485` — настройки RS485-транспорта для этого устройства (обязателен при
    `method=rs485`; при `method=ble` может отсутствовать либо храниться как
    альтернативные настройки):
    - `transport` — `"tcp"` (прозрачный IP-RS485-шлюз, по умолчанию) или `"com"`
      (локальный COM-порт);
    - `address` — `host:port` шлюза (для `transport=tcp`);
    - `port` / `baud` / `data_bits` / `parity` / `stop_bits` — параметры COM-порта
      (по умолчанию 19200 8N1);
    - `port_type` — **физический порт BMS**, к которому подключён шлюз:
      `"rs485"` (верхний host-RS485, read-команды без INFO; по умолчанию) или
      `"rm485"` (инверторный RM485, для `0x42` нужен `INFO=[00]`);
    - `unit` — адрес в кадре PACE (поле **ADR**), подставляется как есть. Для этой
      BMS живой опрос идёт с `ADR=0`, поэтому `unit=0` (не 1). Это **не** Modbus
      unit id — у PACE адресация 0-based.
- **BLE-имя не используется.** У всех EnBMS заводское имя одинаковое (`BP00`),
  поэтому оно не читается и не является идентификатором. Отображаемое имя =
  `<name> <ключ>` (если `name` пуст — `BMS <ключ>`).

> **Период EnBMS задаётся в этом разделе, а не в `poll`.** В обязательном разделе
> `poll` поля `enbms` больше нет — период у каждого метода свой.

### Пример: BLE (Bluetooth)

Устройство опрашивается по Bluetooth Low Energy. Обязателен `mac` (подключение
идёт по адресу), блок `rs485` не нужен:

```json
"enBms": {
  "disabled": false,
  "poll_interval_ble": 3,
  "poll_interval_rs485": 1,
  "devices": [
    { "name": "BMS EnBMS #1", "mac": "AA:BB:CC:11:22:33", "method": "ble", "disabled": false }
  ]
}
```

### Пример: RS485 через прозрачный TCP-шлюз

Устройство опрашивается по RS485 через прозрачный IP-RS485-шлюз (`transport="tcp"`)
— так сейчас подключено на проде. Задаётся `address` (host:port шлюза):

```json
"enBms": {
  "disabled": false,
  "poll_interval_ble": 3,
  "poll_interval_rs485": 1,
  "devices": [
    { "name": "BMS EnBMS #2", "mac": "AA:BB:CC:44:55:66", "method": "rs485", "disabled": false,
      "rs485": { "transport": "tcp", "address": "192.168.0.77:502", "port_type": "rs485", "unit": 0 } }
  ]
}
```

### Пример: RS485 через COM-порт

Тот же RS485, но транспорт — локальный COM-порт (например, USB-RS485-адаптер на
машине с sunReceiver). Вместо `address` задаётся `port` и параметры линии:

```json
"enBms": {
  "disabled": false,
  "poll_interval_ble": 3,
  "poll_interval_rs485": 1,
  "devices": [
    { "name": "BMS EnBMS #3", "mac": "AA:BB:CC:44:55:66", "method": "rs485", "disabled": false,
      "rs485": {
        "transport": "com",
        "port": "/dev/ttyUSB0",
        "baud": 19200,
        "data_bits": 8,
        "parity": "none",
        "stop_bits": 1,
        "port_type": "rs485",
        "unit": 0
      } }
  ]
}
```

- `port` — имя порта: `/dev/ttyUSB0` (Linux), `COM3` (Windows).
- `baud` / `data_bits` / `parity` / `stop_bits` — необязательны (по умолчанию
  19200 8N1); `parity` — `none` | `even` | `odd`; `stop_bits` — `1` | `2`.
- `address` при `transport=com` не задаётся.

## Транспорт BLE и протокол

| Роль | UUID |
|---|---|
| Сервис | `0000ff00-…` |
| Запись команд (host→BMS) | `0000ff02-…` |
| Уведомления/ответы (BMS→host) | `0000ff01-…` |

Кадр (big-endian), CRC-16/CCITT (полином `0x1021`, init 0) по `frame[1:len-3]`:

```
Запрос: 7E 10 ADR 46 CID2 LEN(2) INFO CHKSUM(2) 0D            (INFO с 7)
Ответ:  7E 14 ADR CID2 RTN LEN(2) INFO CHKSUM(2) 0D           (INFO с 7)
```

Полная длина = `10 + LENID` (`LENID = frame[5]<<8 | frame[6]`), CRC — по
`frame[1:len-3]`. Сборка — **строго по длине**, а не по `0x0D`: байт `0x0D`
встречается внутри payload. Ответ приходит несколькими notify-фрагментами —
склеиваются в буфере.

> Формат подтверждён живыми кадрами Battery/BasicInfo (CRC-16/CCITT). В
> `DEVICE_SNAPSHOT.md` полные кадры приведены без байта `RTN` — ориентироваться
> на живые (в тестах модуля зафиксирован реальный кадр).

Запрос Battery: `7E 10 00 46 61 00 01 00 <crc> 0D`.

### Payload Battery (106 Б)

`dataflag(u8) slaveNo(u8) batterynum(u8) cells[batterynum×u16, мВ] tempnum(u8)
temps[tempnum×u16, 0.1 K] current(s16, 0.01 А) totalV(u16, 0.01 В)
remaining(u16, 0.01 А·ч) customerp(u8) totalCap(u16, 0.01 А·ч) soc(u16, 0.1 %)
ratedCap(u16, 0.01 А·ч) cycles(u16) soh(u16, 0.1 %) portV(u16, 0.01 В) warnings…`

Мощность протоколом отдельно не отдаётся — считается `P = totalV × current`.

**Знак тока/мощности.** В протоколе EnBMS поле `chargecurrent` (`s16`) имеет
семантику «минус = разряд». В проекте принято обратное соглашение — **разряд
положительный, заряд отрицательный** (как у ANT BMS), поэтому знак тока
инвертируется при разборе; мощность (`U·I`) наследует правильный знак.

## Транспорт RS485 (ASCII PACE)

На RS485 используется **не** бинарный кадр BLE, а ASCII-hex диалект семейства
YD/T 1363 (PACE):

```
Запрос:  ~ VER(2) ADR(2) 46 CID2(2) LEN(4) INFO(hex) CHK(4) CR
Ответ :  ~ VER(2) ADR(2) 46 RTN(2) LEN(4) INFO(hex) CHK(4) CR
```

- `VER = 0x20`, `CID1 = 0x46`; `ADR = unit` (значение из `rs485.unit` конфига,
  подставляется как есть; для этой BMS `unit=0`).
- `LEN = LCHKSUM<<12 | LENID`, `LENID = len(INFO)` (в запросе — байты, в ответе —
  hex-символы); `CHK` — 16-битное дополнение суммы ASCII-кодов от `VER` до `INFO`.
- `RTN = 0x00` — успех; иное — ошибка (в т.ч. `0x03` LenCheck, `0x04` No Support).
- Телеметрия — CID2 `0x42` (TeleMeter, 75 Б). На **host-RS485** INFO не нужен; на
  **RM485** для `0x42`/`0x44` требуется `INFO=[00]` (`port_type="rm485"`).
- Раскладка INFO TeleMeter до напряжения клемм совпадает с BLE Battery, поэтому
  разбор телеметрии общий (`parseEnBmsBatteryPayload`). Напряжения ячеек, ток,
  ёмкости, SOC/SOH, циклы — те же. **Сигнального хвоста предупреждений у `0x42`
  нет** (после клемм идут temp-drift/zero-current/энергии), поэтому алармы из
  хвоста по RS485 не разбираются (для алармов есть CID2 `0x44` — в будущем).
- Реализация транспорта: TCP (`net.Dial`, постоянное соединение) или COM-порт
  (`go.bug.st/serial`).
- Байт `0x0D` не может встретиться внутри hex-ASCII payload, поэтому ответ
  читается до `CR` (в отличие от BLE, где кадр собирается по длине).

Живой реверс и полные карты `0x42`/`0x44`/`0x47` — `/home/sasha/src/energybms/protocol-485.md`.

## Принципы работы (по образцу CE308 и ANT BMS)

- **Соединение постоянное**: пулер держит соединение с каждым устройством и не
  рвёт его между опросами; при обрыве переподключается. BLE — ограниченный
  бэкофф (2…30 с); RS485 — попытка ограничена 5 с, при неудаче пауза 15 с и
  повтор (постоянное TCP-соединение со шлюзом переустанавливается). Транзиентный
  таймаут чтения ретраится (до 3 попыток) без разрыва связи; после 3 подряд
  неудачных опросов соединение переустанавливается.
- **Последовательный опрос**: устройства опрашиваются по одному с периодом
  активного метода (`enBms.poll_interval_ble` / `enBms.poll_interval_rs485`; если
  суммарное чтение дольше — паузы нет).
- **Устойчивость BLE**: переиспользуются хелперы CE308 — управление питанием
  адаптера и перенацеливание tinygo на реальный `hciN`, сброс «залипшего»
  состояния BlueZ, discovery, если устройство не известно BlueZ.
- **Лимит BT-устройств**: для BLE суммарное число BLE-устройств (EnBMS + CE308) не
  должно превышать `enbmsMaxBTDevices` (5); иначе опрос EnBMS не запускается, в лог
  пишется ошибка. Для RS485 лимита нет.
- **Завершение по SIGTERM**: цикл опроса проверяет контекст, закрывает соединения
  и корректно завершается; незавершённый 5-минутный бакет в PG не пишется.

## Хранение и усреднение

Схема — как у ANT BMS:

- Redis `sunreceiver:enbms:current` (HASH, поле = ключ устройства: MAC, иначе name) — текущий снимок;
- Redis `sunreceiver:enbms:series:<YYYY-MM>` (ZSET) — **каждое снятое показание**
  (score = секунда, `samples=1`; окно 2 суток, чистка PurgeOld);
- PostgreSQL `sunreceiver.enbms_averages` (`name`=ключ, `ts`, `values` jsonb) —
  вся история с гранулярностью **1 запись / 5 минут**; вставка с sample-count guard;
- неполный 5-минутный промежуток при остановке в PG не пишется (только полные
  бакеты); в Redis он не нужен — сырые показания уже записаны.

При полностью пустом Redis ряд `enbms:series` восстанавливается из PG
(`EnBmsAveragesAll`) — восстановленный участок представлен 5-минутными средними
(`samples>1`), до первых новых опросов ряд смешанный.

Мгновенные поля (ток/мощность/SOC/ёмкости/напряжения ячеек/температуры)
усредняются за 5 минут; дискретные (число ячеек, циклы) берутся по последнему
снимку. Ряд на дашборде прореживается `downsampleBMSSeries` (порог + усреднение),
как и остальные графики.

## Дашборд

EnBMS выводится на дашборд тем же API, что и ANT BMS, — с приведением к форме
`bmsDevice`/`bmsSeriesPoint` и полем `kind="enbms"`:

- `/api/bms` — «батарейки» на главной (блок `BMS (батареи)` включается, если
  настроен ANT BMS или EnBMS; сортировка — по отображаемому имени);
- `/api/bms/<MAC>` и `/api/bms/<MAC>/series` — страница деталей `/bms/<MAC>`
  (карточки, ячейки, температуры, графики: свежая часть — сырые точки из Redis,
  старая — 5-мин средние из PG, ряд прореживается на стороне API).

Отображаемое имя EnBMS — `<name> <ключ>` (BLE-имя не уникально; ключ (MAC, иначе
name) виден под батарейкой на главной и в заголовке страницы `/bms/<ключ>`).

Чего в блоке Battery нет (состояния мощностных ключей/балансировки, счётчик
кадров), фронт скрывает по `kind`; отсутствующие у EnBMS поля остаются нулевыми.

## Сигнальный хвост Battery: аварии и балансировка (2026-10-01)

Отдельный CID2 0x44 (`TeleState`) на устройстве недоступен, но предупреждения
приложение получает из **хвоста блока Battery (0x61)**. Раскладка восстановлена из
APK (`parseBody_Battery`, `BmsMsgUtil.dart` `0x3f3a18`; порядок имён — `toJson`
`0x3def6c`): хвост = **39 байт** после телеметрии (INFO=106 Б, телеметрия=67 Б).

| Смещение в хвосте | Байт | Смысл |
|---|---|---|
| 0–15 | 16 (`batterynum`) | warn-список по ячейкам |
| 16–19 | 4 (`tempnum−2`) | warn-список по температурам |
| 20 | 1 | `envtempwarn` |
| 21 | 1 | `powertempwarn` |
| 22 | 1 | `chargecurrentwarn` |
| 23 | 1 | `customerwarnp` |
| 24…38 | — | статусы (`eventwarnlist`, ключи, балансировка, `sysstate`, `brokenstatelist`) |

**Ключевое:** warn-область (смещения 0…23) на здоровом кадре **нулевая**; ненулевые
байты `01 03 08` (смещения 25…27) — это **статусы** (ключ/балансировка/режим), а не
аварии. Декодер (`parseEnBmsTail`) читает аварии только из warn-области, поэтому
ложных плашек нет.

> ⚠️ Ошибочный путь (отвергнут): декодировать аварии из `Ext_Bit`
> XML `teleSignal_Group` (смещение tail[24:38]) — этот XML описывает протокол ПО
> «Upper Computer» (CID2 0x42/0x44), а не Battery (0x61), и даёт ложные срабатывания.
> Статусы (ключи/баланс/режим) пока не декодируются — их смещения не подтверждены.
> Подробный реверс — `energybms/PROTOCOL.md` §5.1.1 и `REVERSE_ENGINEERING.md` §2.1.

### Сырой лог телеметрии (калибровка)

Пулер пишет payload телеметрии (hex) в журнал (`enbms: RAW ...`) с таймстампом
снятия: при **изменении** сигнального хвоста (только BLE) и не реже одного раза в
60 с (`enbmsRawLogInterval`). На Windows журнал — файл `sunReceiver.log` рядом с
бинарником; на Linux — journald. Формат строки:

```
enbms: RAW <name> (<ключ>) ts=<RFC3339> tail=<hex 39Б> payload=<hex INFO>
```

`tail` заполняется **только для BLE** (Battery 0x61); у RS485 TeleMeter (0x42)
он пуст — поля после напряжения клемм другие. Warn-область даёт корректный
результат (на здоровом кадре пусто); запись алармов EnBMS в `device_errors`
(device=`<ключ>`, kind=`enbms`) ведётся по появлению новых алармов. Телеметрию
алармы не затрагивают.
