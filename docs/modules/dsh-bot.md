# maxbot: чат с DeepSeek Harness (dsh)

`cmd/maxbot` выполняет две роли:

1. **Уведомления** — читает Redis Stream `sunreceiver:notify:events` и отправляет
   события МАП в MAX (см. [`notify.md`](notify.md)).
2. **Прокси-чат с DeepSeek Harness** — оператор пишет в MAX, maxbot передаёт
   запрос в harness и возвращает ответ агента. Кроме ответов отправляются
   служебные сообщения о состоянии («Принято, в очереди: N», «Агент работает»,
   смена модели, ошибки). Настройки — раздел `dsh` в `maxbot.json`.

## Как устроен harness на проде

- systemd-юнит `deepseek-harness.service` (dsh 0.2.2+), слушает
  `http://127.0.0.1:3080` на том же хосте, где работает maxbot.
- **Launch token** печатается процессом dsh в journald. maxbot извлекает его
  (`journalctl -u deepseek-harness -o cat`, regex `token=...`) и меняет на
  подписанную cookie: `GET /connect?token=<token>&interactions=none`.
- Дальше — unary HTTP: `POST /api/<method>` с конвертом
  `{"type":"client-request","rpcId":"...","method":"...","payload":{"args":{...}}}`.
  Ответ — `{"type":"server-response","rpcId":"...","result":{"ok":true,"value":...}}`.
- Используются методы: `session/modelCatalog`, `session/create`,
  `session/selectModel`, `session/prompt`, `session/wait`, `session/events`,
  `session/cancel`.

Токен и cookie **не хранятся в конфиге**. При 401 (перезапуск harness) maxbot
перечитывает токен и заново выполняет `/connect`.

### Требования к окружению

- maxbot должен читать журнал: пользователь `maxbot` входит в группу
  `systemd-journal`.
- maxbot должен писать входящие файлы в `/opt/dsh-bot` (юнит:
  `ReadWritePaths=/opt/dsh-bot`), каталог принадлежит `maxbot:maxbot`.
- Harness уже настроен на `wbllm/coder-medium/low` и полный доступ агента
  (`danger-full-access`). Отдельных прав/параметров в API запроса не требуется.

## Конфигурация `maxbot.json`

```json
"dsh": {
  "disabled": false,
  "base_url": "http://127.0.0.1:3080",
  "workspace": "/opt/dsh-bot",
  "incoming_dir": "/opt/dsh-bot/incoming",
  "provider": "wbllm",
  "default_model": "coder-medium",
  "effort": "low",
  "model_ttl_hours": 2,
  "heartbeat_sec": 180,
  "retry_attempts": 3,
  "token_unit": "deepseek-harness"
}
```

- `disabled=true` или отсутствие раздела `dsh` — чат выключен, уведомления
  работают как раньше.
- `base_url` — адрес harness (по умолчанию `http://127.0.0.1:3080`); при
  заданном значении проверяется http(s)+host. `workspace` — рабочий каталог
  агента (по умолчанию `/opt/dsh-bot`).
- `effort` всегда передаётся как уровень усилия, если модель его поддерживает
  (`low` по требованию); иначе параметр не передаётся.
- `heartbeat_sec` ограничен сверху 180 (требование «не реже раза в 3 минуты»).
- Сообщения принимаются только от `user_id` из `allowed_user_ids`; оператор
  обязан входить в этот список.

Публичный пример — `maxbot.sample.json`.

## Команды меню

- `/menu` — основное меню кнопками: Модель, Статус, Отмена, Продолжить,
  Новая сессия.
- `/model` — inline-клавиатура с доступными моделями обоих провайдеров
  (`wbllm`, `deepseek-official`), по одной модели в строке, по 25 на страницу
  (кнопки «Назад/Ещё»), текущая модель отмечена `✓`. Выбор применяется к текущей
  сессии.
- `/cancel` — прерывает текущий ход и очищает очередь.
- `/new` — прерывает ход, очищает очередь и создаёт новую сессию.
- `/continue` — отправляет агенту «продолжи с места остановки».
- `/status` — модель, сессия, длина очереди, остаток окна модели.

Любой другой текст от разрешённого `user_id` — промпт агенту (включая
`/compact` и прочие слэш-команды harness; перехватываются только команды выше).

## Поведение

- **Очередь**: запросы выполняются строго по одному. Пока агент занят, новое
  сообщение ставится в очередь и подтверждается («Принято, в очереди: N»).
- **Контекст**: одна сессия с постоянным контекстом; сессия и курсоры хранятся в
  Redis и переживают рестарт maxbot.
- **Модель**: по умолчанию `wbllm/coder-medium`. Выбранная модель живёт 2 часа
  **простоя**; окно продлевают промпты, ожидание ответа, вопросы/ответы и
  активный отложенный ход. Фоновые проверки watcher (`session/state`) окно НЕ
  продлевают. По истечении окна модель сбрасывается на `coder-medium`, оператор
  получает уведомление.
- **Heartbeat**: пока агент работает, отправляется «Агент работает». Проверка
  выполняется после каждого `session/wait` (30 с), поэтому фактический интервал
  может быть до ~30 с больше `heartbeat_sec`; сам `heartbeat_sec` ограничен 180 с.
- **Отложенные задачи агента** (`schedule_create`): результат срабатывания
  появляется в той же сессии без нового промпта. Фоновый watcher раз в 3 с
  проверяет `session/state`, когда воркер свободен, и ориентируется на
  `running`/непустую очередь harness (поле `active` постоянно true у живой
  сессии и признаком хода не является). После завершения хода доставляется
  только **финальный** видимый `text`-блок (последний `assistant/message` перед
  `turn/end`); промежуточные сообщения («Проверяю…») и reasoning не
  отправляются. Курсор доставки (`last_answer_seq`) и хвост незавершённого хода
  сохраняются в Redis: после рестарта уже доставленное не дублируется, а хвост
  будет доставлен при завершении хода. Доставка — at-most-once: если процесс
  упадёт или MAX вернёт ошибку между сохранением курсора и отправкой, этот
  ответ может быть потерян (повторно не отправляется). Сбой/цикл/переполнение
  в отложенном ходе обрабатываются по общим правилам замены сессии.
- **Вопрос агента** (`input-required`): текст вопроса пересылается оператору;
  текущий ход автоматически останавливается (ответить на живой `ask_user_question`
  через unary-API нельзя), а следующее сообщение оператора идёт новым промптом в
  той же сессии. Повторные уведомления по одному и тому же вопросу подавляются.
- **Вложения**: изображения передаются в harness как base64 `image`-блок;
  файлы сохраняются в `incoming_dir/<YYYY-MM-DD>/` и передаются агенту путём в
  тексте промпта.
- **Длинный ответ** (> 4000 символов) отправляется файлом `.md`/`.txt`
  (эвристика по разметке); при ошибке загрузки — частями текста.
- **Формат**: Markdown; при ошибке отправки — fallback на plain text.

### Замена сессии

Сессия заменяется автоматически при:

- `CONTEXT_WINDOW_EXCEEDED` в `turn/end`;
- `turn/end` с `max-tokens`;
- цикле `tool/call`: период 1–6 вызовов, блок повторяется 3 раза подряд
  (отпечаток — имя + канонический JSON аргументов, история копится между
  ходами);
- трёх подряд финальных ответах со сходством ≥ 90% (нормализованный текст,
  только ответы длиннее 80 символов).

При замене: старая сессия отменяется, создаётся новая, оператору уходит
уведомление, агент получает запрос «найди историю предыдущей сессии и восстанови
хвост и ключевые факты». Текущий запрос один раз возвращается в очередь и
выполняется уже в новой сессии. Ручная замена — `/new`.

По таймауту без событий сессия **не** меняется (только по ошибкам/циклам).

## Redis

| Ключ | Назначение |
|---|---|
| `sunreceiver:maxbot:dsh:state` | HASH: сессия, модель, курсоры событий/ответов, история tool-вызовов, последние ответы |
| `sunreceiver:maxbot:dsh:queue` | LIST: очередь запросов (LPUSH/BRPOPLPUSH) |
| `sunreceiver:maxbot:dsh:processing` | LIST: запрос в работе (возвращается в очередь после рестарта) |
| `sunreceiver:maxbot:max_marker` | marker long polling MAX (чтобы не дублировать сообщения после рестарта) |

Очередь уведомлений `sunreceiver:notify:events` не затрагивается.

При рестарте/падении maxbot незавершённый элемент из `processing` возвращается в
очередь и выполняется раньше более новых. `requestId` сохраняется в элементе,
поэтому повторная отправка дедуплицируется harness (тот же `requestId` не создаёт
второе сообщение). Если harness недоступен и все `retry_attempts` исчерпаны,
запрос не возвращается в очередь автоматически: оператор получает ошибку и
может повторить его через `/continue` или новым сообщением.

## Ограничения

- Long polling MAX не рекомендован документацией для production; текущая схема
  оставлена, конфиг/интерфейс заложены под будущий webhook.
- Вопрос агента не «привязывается» к ответу оператора: ответ уходит новым
  промптом; при зависании используйте `/cancel`.
- Ограничение текста MAX — 4000 символов; более длинные ответы уходят файлом.
- Вложения скачиваются воркером перед отправкой промпта. Ссылки MAX имеют
  ограниченный срок жизни: если файл долго пролежал в очереди и ссылка истекла,
  оператор получает уведомление об ошибке скачивания и может отправить файл
  повторно.
