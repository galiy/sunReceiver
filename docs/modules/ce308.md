# Счётчик Энергомера CE308 (опрос по BLE)

Модуль опрашивает счётчик Энергомера **СЕ308** (трёхфазный многофункциональный)
по **Bluetooth Low Energy** и пишет данные в Redis/PostgreSQL. Протокол обмена и
структура BLE-сервиса — локальный `~/src/ce308/docs/PROTOCOL.md` (кампания
исследования и снятия показаний — `~/src/ce308/docs/`).

## Раздел конфига `ce308`

```json
"ce308": {
  "disabled": false,
  "name": "CE308 #194232482",
  "mac": "6C:B2:FD:70:BD:FF",
  "pin": "324742"
}
```

| Поле | Значение |
|--|--|
| `disabled` | **обязательно** (`false` — опрашивается; `true` — опрос CE308 отключён, пулер/аккумулятор не запускаются) |
| `name` | имя Bluetooth-устройства (BT-имя), используется как ключ идентификатора в Redis/PG и для отображения |
| `mac` | **BD_ADDR** счётчика (адрес для BLE-подключения) |
| `pin` | **BLE-PIN** радиоинтерфейса (6 цифр), используется при спаривании |

Пароль в открытом виде (конфиг приватный, в git не выгружается); в
`sunReceiver.sample.json` замазан.

## Поток данных

`CE308 → BLE → ce308_poller (2 с) → Redis (current + series) → ce308_accumulator → PG (10-с средние)`

- **Текущие значения** — перезаписываются после каждого успешного опроса
  (`sunreceiver:ce308:current`).
- **История** — ~1 точка за 2 с в Redis-ряду (`sunreceiver:ce308:series:<YYYY-MM>`),
  время удержания — 2 календарных суток (PurgeOld).
- **PG** — усреднение до **1 записи за 10 секунд** (в отличие от 5-минутных
  агрегатов инверторов): собственная таблица `sunreceiver.ce308_averages` с PK
  `(name, ts)` — эффективный range-scan «устройство за период времени».

## Логируемые параметры (мгновенные)

В `values` снимка попадают теги (единица в суффиксе):

| Тег | Единица | Источник |
|--|--|--|
| `ce308_l1_voltage` / `l2` / `l3` | В | `VOLTA()` |
| `ce308_l1_current` / `l2` / `l3` | А | `CURRE()` |
| `ce308_l1_active_power` / `l2` / `l3` / `ce308_active_power` (Σ) | Вт | `POWEP()` ×1000 |
| `ce308_l1_reactive_power` / `l2` / `l3` / `ce308_reactive_power` (Σ) | вар | `POWEQ()` ×1000 |

Значения округляются до 1 знака. **Время актуальности** — `Timestamp` снимка
(момент снятия), передаётся как `timestamp` (RFC3339).

## Жизненный цикл потока

- Поток **держит BLE-соединение постоянно** (не закрывает между опросами).
- **Реконнект сам**: при обрыве соединение закрывается и переустанавливается
  с паузой (2 с); логи сбоев подключения — не чаще раза в 10 минут.
- Целевой период — 2 с; фактический ограничен временем последовательного чтения
  4 команд BLE (~4-5 с), поэтому цикл не «накапливает» отставшие тики (ticker
  буферизует один тик и сбрасывает лишние).
- Спаривание: на Linux регистрируется BlueZ-агент (`KeyboardDisplay`), который
  отвечает на запрос passkey значением `pin` — первое подключение происходит
  без ручного ввода PIN. После успешного спаривания агент не нужен.
- **Питание BLE-адаптера** на Linux проверяется программно перед подключением:
  через BlueZ читается `Powered` и при выключенном адаптере он включается
  (`Properties.Set`). Также детектируется фактический id контроллера
  (`hci0`..`hci9`): tinygo жёстко использует `hci0`, а USB-адаптер после
  переинициализации может стать `hci1`/`hci2` — тогда `DefaultAdapter`
  перенацеливается на реальный контроллер. На Windows/macOS — no-op.
- **Валидация показаний**: после чтения (`VOLTA/CURRE/POWEP/POWEQ`) снимок
  проверяется (наличие всех фаз и Σ, отсутствие NaN/Inf, грубые физические
  диапазоны напряжения/тока/мощности). Кривой снимок из-за нестабильного
  BLE-канала отбрасывается **без** разрыва постоянного соединения.

## Разовый снимок энергии

Снимок энергии снимается **и по внешнему сигналу, и автономно**:

- **По сигналу** (`POST /api/ce308/energy`) пулеру передаётся запрос снять показания
  энергии — в ближайшем цикле читаются команды и сохраняется разовый снимок.
- **Автономно** — раз в **30 минут** (`ce308EnergyInterval`) пулер сам, без внешнего
  запроса, перечитывает `END01..END04` и обновляет снимок. При инициализации модуля
  задержка до первого автоопроса ориентируется на время последнего снимка в Redis
  (`ce308EnergyDelay`): если он свежее периода — ждём до `(last + 30 мин)`, если
  снимка нет или он устарел — снимок снимается сразу.

Считанные показания сохраняются **разовым снимком** в отдельный ключ
`sunreceiver:ce308:energy` (история по энергии не ведётся). Разрезы:
**Актив/Реактив × День/Ночь × Потребление/Отдача** + время актуальности.

| Поле | Смысл | Команда |
|--|--|--|
| `active_consumption_*` | активная потребление A+ | `END01()` |
| `active_delivery_*` | активная отдача A− | `END02()` |
| `reactive_consumption_*` | реактивная потребление R+ | `END03()` |
| `reactive_delivery_*` | реактивная отдача R− | `END04()` |

`*_day` — тариф T1 (день), `*_night` — T2 (ночь), `*_total` — сумма.
Единицы — как отдаёт счётчик: кВт·ч / квар·ч. Чтение `ENDzz()` занимает до
~25-45 с каждая, поэтому в этот период опрос мгновенных значений приостанавливается
и возобновляется после снятия снимка.

## HTTP API дашборда

| Маршрут | Метод | Что отдаёт |
|--|--|--|
| `/api/ce308/current` | GET | текущий снимок CE308 (мгновенные значения + время актуальности) |
| `/api/ce308/energy` | GET | последний разовый снимок энергии (404, если ещё не было) |
| `/api/ce308/energy` | POST | сигнал снять показания энергии (202 + `accepted:true/false`) |
| `/api/ce308/series?from&to` | GET | история суммарной активной мощности CE308 (Redis + PG) |

## Файлы

- `ce308_client.go` — BLE-транспорт (tinygo.org/x/bluetooth, BlueZ), кадры IEC 61107.
- `ce308_agent_linux.go` / `ce308_agent_other.go` — BlueZ-агент PIN (Linux) / заглушка.
- `ce308.go` — конфиг-раздел, маппинг values, парсинг энергоснимка.
- `ce308_poller.go` — 2-с цикл, реконнект, обработка сигнала энергоснимка.
- `ce308_store.go` — Redis-ключи current/series/energy и выборка истории.
- `ce308_accumulator.go` — усреднение 10-с промежутков в PG.
- `ce308_test.go` — тесты маппинга значений и парсинга энергии.

## Замечания по эксплуатации

- Для BLE нужен поддерживающий LE-контроллер (BlueZ на Linux) и счётчик в зоне
  видимости; классический BT 2.0 (HCI 2.0) не подходит.
- Счётчик должен «вещать» по BLE (иногда требуется активировать радиоканал).
- Если устройство ещё не спарено с хостом, первое подключение выполняется
  агентом с PIN из конфига; если хост сконфигурирован иначе — потребуется
  предварительное спаривание (`bluetoothctl`).
