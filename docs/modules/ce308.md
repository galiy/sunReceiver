# Счётчик Энергомера CE308 (опрос по BLE)

Модуль опрашивает счётчик Энергомера **СЕ308** (трёхфазный многофункциональный)
по **Bluetooth Low Energy** и пишет данные в Redis/PostgreSQL. Протокол обмена и
структура BLE-сервиса — локальный `~/src/ce308/docs/PROTOCOL.md` (кампания
исследования и снятия показаний — `~/src/ce308/docs/`).

> **Откуда берётся BLE-адаптер (важно при диагностике «адаптер пропал»).**
> Сейчас на `.253` используется **штатный физический USB Bluetooth-адаптер**
> (Realtek `0bda:8771`, `RTK_BT_5.0`; контроллер `hciN`, обычно `hci0`). Ранее
> контроллер был **проброшен по usbip с `.9`** (MediaTek MT7921K), но этот
> проброс **отключён и удалён с обоих хостов 2026-09-24** — историческое
> описание, снимки конфигов и порядок восстановления см. в
> [`../ce308-bluetooth/`](../ce308-bluetooth/). Для диагностики важно, что
> `ce308EnsurePowered` сам находит фактический `hciN` и перенацеливает tinygo
> `DefaultAdapter` (см. ниже), поэтому перенумерация адаптера не требует
> перезапуска сервиса.

## Раздел конфига `ce308`

```json
"ce308": {
  "disabled": false,
  "name": "CE308 #000000000",
  "mac": "AA:BB:CC:DD:EE:FF",
  "pin": "CHANGE_ME_PIN"
}
```

| Поле | Значение |
|--|--|
| `disabled` | **обязательно** (`false` — опрашивается; `true` — опрос CE308 отключён, пулер/аккумулятор не запускаются) |
| `name` | имя Bluetooth-устройства (BT-имя), используется как ключ идентификатора в Redis/PG и для отображения |
| `mac` | **BD_ADDR** счётчика (адрес для BLE-подключения) |
| `pin` | **BLE-PIN** радиоинтерфейса (6 цифр), используется при спаривании |

Пароль в открытом виде (конфиг приватный, в git не выгружается); в
`sunReceiver.sample.json` замазан.

## Поток данных

`CE308 → BLE → ce308_poller (2 с) → Redis (current + series) → ce308_accumulator → PG (10-с средние)`

- **Текущие значения** — перезаписываются после каждого успешного опроса
  (`sunreceiver:ce308:current`).
- **История** — ~1 точка за 2 с в Redis-ряду (`sunreceiver:ce308:series:<YYYY-MM>`),
  время удержания — 2 календарных суток (PurgeOld).
- **PG** — усреднение до **1 записи за 10 секунд** (в отличие от 5-минутных
  агрегатов инверторов): собственная таблица `sunreceiver.ce308_averages` с PK
  `(name, ts)` — эффективный range-scan «устройство за период времени».

## Логируемые параметры (мгновенные)

В `values` снимка попадают теги (единица в суффиксе):

| Тег | Единица | Источник |
|--|--|--|
| `ce308_l1_voltage` / `l2` / `l3` | В | `VOLTA()` |
| `ce308_l1_current` / `l2` / `l3` | А | `CURRE()` |
| `ce308_l1_active_power` / `l2` / `l3` | Вт | `POWEP()` ×1000 |
| `ce308_active_power` (Σ) | Вт | **знаковая сумма** фаз L1+L2+L3 (не поле Σ счётчика) |
| `ce308_l1_reactive_power` / `l2` / `l3` | вар | `POWEQ()` ×1000 |
| `ce308_reactive_power` (Σ) | вар | **знаковая сумма** фаз L1+L2+L3 (не поле Σ счётчика) |

Итог по мощности (Σ) — алгебраическая сумма трёх фаз по знаку: фазы могут быть
взаимоисключающими (одна отдаёт в сеть, другая потребляет), поэтому знаковая сумма
физически корректна. Это значение используют и таблица дашборда, и графики, и
анимация — единый источник истины (теги `ce308_active_power`/`ce308_reactive_power`).

Значения округляются до 1 знака. **Время актуальности** — `Timestamp` снимка
(момент снятия), передаётся как `timestamp` (RFC3339).

## Жизненный цикл потока

- Поток **держит BLE-соединение постоянно** (не закрывает между опросами).
- **Реконнект сам**: при обрыве соединение закрывается и переустанавливается
  с ограниченным бэкоффом (базовая пауза 2 с, удваивается после каждой неудачной
  попытки до 30 с, сбрасывается при успешном подключении); логи сбоев
  подключения — не чаще раза в 10 минут.
- **Устойчивость к одиночным сбоям чтения** (нестабильный радиоканал):
  - **Таймаут ответа** одного чтения (`VOLTA/CURRE/POWEP/POWEQ`) — транзиентный
    сбой радио: чтение ретраится (до `ce308ReadRetries` повторных попыток),
    постоянное соединение НЕ разрывается.
  - **Ошибка записи/транспорта** — соединение, вероятно, оборвано: чтение не
    ретраится, ошибка уходит вверх.
  - Соединение разрывается и переустанавливается только после
    **`ce308ConsecutiveFailLimit` опросов подряд** (`3`); одиночные неудачи
    логируются (`опрос ... не удался (N подряд) — соединение сохраняю`) и
    сбрасываются при следующем успехе (`связь восстановлена`). Это убирает
    «заморозку» данных на ровном месте из-за одного неудачного чтения.
- **Восстановление** после потери связи: пулер сначала пробует **прямой Connect**
  по MAC (скан не нужен, если BlueZ «знает» устройство — объект
  `/org/bluez/<hci>/dev_*` существует, т.к. счётчик спарен/обнаружен ранее).
  Короткий discovery (`ce308DiscoveryTimeout`, 8 с) — только **fallback**, когда
  прямого объекта нет (например, после смены/переинициализации адаптера); после
  discovery Connect повторяется. Discovery больше не является обязательным
  предусловием подключения — зависший сканер не блокирует прямой connect.
- Целевой период — 2 с; фактический ограничен временем последовательного чтения
  4 команд BLE (~4-5 с), поэтому цикл не «накапливает» отставшие тики (ticker
  буферизует один тик и сбрасывает лишние).
- Спаривание: на Linux регистрируется BlueZ-агент (`KeyboardDisplay`), который
  отвечает на запрос passkey значением `pin` — первое подключение происходит
  без ручного ввода PIN. После успешного спаривания агент не нужен.
- **Питание BLE-адаптера** на Linux проверяется программно перед подключением:
  через BlueZ читается `Powered` и при выключенном адаптере он включается
  (`Properties.Set`). Также детектируется фактический id контроллера
  (`hci0`..`hci9`): tinygo жёстко использует `hci0`, а USB-адаптер после
  переинициализации может стать `hci1`/`hci2` — тогда `DefaultAdapter`
  перенацеливается на реальный контроллер. На Windows/macOS — no-op.
- **Валидация показаний**: после чтения (`VOLTA/CURRE/POWEP/POWEQ`) снимок
  проверяется (наличие всех фаз и Σ, отсутствие NaN/Inf, грубые физические
  диапазоны напряжения/тока/мощности). Кривой снимок из-за нестабильного
  BLE-канала отбрасывается **без** разрыва постоянного соединения.

### Видимость «зависших» данных

Счётчик опрашивается раз в ~2 с, поэтому отсутствие обновлений заметно сразу.
На дашборде метка «Актуально:» у CE308 окрашивается в красный (класс `stale-time`)
и в tooltip показывает возраст снимка, если он старше `CE308_STALE_MS` (20 с) —
аналогично offline-инверторам. Программно пулер также логирует отдельные события
`опрос ... не удался (N подряд)` / `связь восстановлена`, чтобы зависание и его
прекращение были видны в журнале без ручного сравнения времени.

### Внешний watchdog авто-восстановления (УСТАРЕЛО И УДАЛЕНО)

> **Устарело и удалено с `.253` (2026-09-24). Ниже — только историческая справка.**
> Этот watchdog (`sunreceiver-watchdog`, перезагрузка `btusb`, «зависший RTL-адаптер»)
> был рассчитан на **физический USB-донгл Realtek** на `.253`. Затем адаптер
> на время **пробрасывался по usbip с `.9`** (MediaTek MT7921K) и обслуживался
> `usbip-bt-watchdog.service` на `.253`; теперь проброс **отключён**, а на `.253`
> стоит штатный физический Realtek-адаптер (см. [`../ce308-bluetooth/`](../ce308-bluetooth/)).
> Юниты `sunreceiver-watchdog.timer`/`.service` и скрипт `/opt/sunreceiver/watchdog.sh`
> **удалены**; в текущей схеме их включать не нужно (его `modprobe -r btusb` рвёт
> контроллер). Всё дальнейшее в этом разделе — как было устроено на физическом
> донгле, для истории.

Помимо устойчивости внутри пулера, на продакшен-хосте сервиса (вне Go-приложения)
работает **внешний watchdog** под root через systemd (`sunreceiver-watchdog`).
Он нужен для сценария, который кодом не лечится: зависшая радиопрошивка
**Realtek BT-адаптера** (например, `hci0: command tx timeout` / `-110`) либо
«залипшая» пара в BlueZ — когда связь теряется надолго и пулер сам не в силах её
поднять.

**Логика (шаг за шагом):**

1. Читает свежесть снимка текущих значений CE308 из Redis (`timestamp` в
   `sunreceiver:ce308:current`). Имя устройства, MAC и адрес Redis берутся из
   `sunReceiver.json` (разделы `ce308`/`db`), а не зашиты.
2. Если снимок **устарел больше `CE308_STALE` (30 мин)** — ищет в журнале
   `sunreceiver.service` за последний час (`LOG_WINDOW`, 1 час) **известные
   ошибки подключения**: `le-connection-abort-by-local`, `tx timeout`,
   `Read reg16 failed`, `-110`, `timeout on DiscoverServices`,
   `подключение … не удалось`, `нет ответа счётчика`.
3. Если ошибки найдены **и** с прошлого срабатывания прошло ≥ `CE308_RATE`
   (**30 мин**) — выполняет восстановление и записывает время в state-файл
   (`/run/sunreceiver-watchdog.last`, tmpfs; при перезагрузке сбрасывается,
   тогда watchdog может сработать сразу).

**Восстановление** (порядок отработан вручную и подтверждён):
- `bluetoothctl remove <MAC>` — очистка «залипшей» пары BlueZ;
- `modprobe -r btusb; modprobe btusb` — перезагрузка драйвера адаптера;
- пауза `sleep 8` — дать пулеру переподключиться; **сервис НЕ перезапускаем**.

Рестарт сервиса из восстановления **убран**: он не чинит зависший радиоадаптер
(состояние драйвера/радио переживает рестарт процесса) и лишний раз обрывает
остальные пулы (инверторы, МАП, счётчик). Вместо этого пулер сам выносит
переинициализацию адаптера (см. ниже «Переинициализация адаптера»).

**Кейсы зависания CE308 и чем лечатся:**

1. **Мягкий сбой** — сбой радиопрошивки/разового `Connect` («tx timeout»,
   `-110`, `le-connection-abort-by-local`). Лечится перезагрузкой драйвера
   `btusb` (watchdog или ручной повтор тех же действий) **без рестарта сервиса**:
   пулер после переинициализации адаптера переподключается сам (см.
   «Переинициализация адаптера»). Штатный случай.
2. **Зависание пулера на `Connect`** — раньше D-Bus `Connect` без дедлайна
   блокировал горутину пулера навсегда; пулер не возвращался в reconnect-цикл,
   и любая переинициализация адаптера не помогала. Закрыто таймаутом на `Connect`
   (20 с, `ce308ConnectTimeout`): пулер обязательно возвращается в цикл повторов.
3. **Аппаратный отказ RTL-адаптера** — контроллер не отвечает на HCI-команды
   (`hciconfig`: `Can't get device info` / `Can't read local name: Connection
   timed out`), при этом прошивка загружается, но радио молчит. Перезагрузка
   драйвера **не помогает** — контроллер лишь получает новый номер
   (`hci0→hci3→hci5→hci6`). Требуется **пересадка USB-адаптера** или
   **перезагрузка хоста** (см. `realtek-bluetooth/README.md`). Ни watchdog, ни
   рестарт сервиса это не лечат.

**Переинициализация адаптера (пулер переживает её без рестарта сервиса):**
- перед каждой попыткой подключения пулер сбрасывает кэш id адаптера
  (`ce308AdapterIDReset`) и `ce308EnsurePowered` **всегда** перенацеливает tinygo
  `DefaultAdapter` на фактически обнаруженный контроллер — в журнале видно
  `BLE-адаптер обнаружен как hciN (tinygo перенацелен с hci0)`;
- поэтому после перезагрузки `btusb` (или пересадки USB, либо перенумерации
  контроллера) пулер сам находит новый `hciN` и переподключается — сервис
  перезапускать не нужно.

**Логирование:** все решения пишутся в syslog через `logger -t sunreceiver-watchdog`
(на Ubuntu journald принимает `/dev/log`): «данные свежие (возраст Nс)», «снимок
устарел … проверяю логи», «ошибки есть», «выполнено: очистка пары + перезагрузка
btusb (без рестарта сервиса — пулер переподключится сам)». Свежий снимок
сбрасывает rate-limit, поэтому при новом сбое watchdog снова может сработать.

**Установка (systemd, от root):**

```sh
# скрипт
/opt/sunreceiver/watchdog.sh                              # rwxr-xr-x, root:root
# юниты
/etc/systemd/system/sunreceiver-watchdog.service          # Type=oneshot, ExecStart=.../watchdog.sh
/etc/systemd/system/sunreceiver-watchdog.timer            # каждые 5 мин
systemctl daemon-reload
systemctl enable --now sunreceiver-watchdog.timer
```

Таймер запускает сервис каждые **5 минут** (`OnBootSec=5min`,
`OnUnitActiveSec=5min`, `Persistent=true`); сама операция восстановления при этом
ограничена 30 минутами из-за старения снимка и rate-limit — то есть watchdog
проверяет часто, а действует редко.

**Ограничения:** watchdog определяет проблему только по **известным** ошибкам и
устареванию снимка; если счётчик перестал отвечать без характерных ошибок в
журнале, он ничего не делает (нет диагностируемой причины). Фактическое
пропадание радиоканала счётчика и замена/пересадка USB-адаптера — по-прежнему
операционное действие на сервере.

## Разовый снимок энергии

Снимок энергии снимается **и по внешнему сигналу, и автономно**:

- **По сигналу** (`POST /api/ce308/energy`) пулеру передаётся запрос снять показания
  энергии — в ближайшем цикле читаются команды и сохраняется разовый снимок.
- **Автономно** — раз в **30 минут** (`ce308EnergyInterval`) пулер сам, без внешнего
  запроса, перечитывает `END01..END04` и обновляет снимок. При инициализации модуля
  задержка до первого автоопроса ориентируется на время последнего снимка в Redis
  (`ce308EnergyDelay`): если он свежее периода — ждём до `(last + 30 мин)`, если
  снимка нет или он устарел — снимок снимается сразу.

Считанные показания сохраняются **разовым снимком** в отдельный ключ
`sunreceiver:ce308:energy` (история по энергии не ведётся). Разрезы:
**Актив/Реактив × День/Ночь × Потребление/Отдача** + время актуальности.

| Поле | Смысл | Команда |
|--|--|--|
| `active_consumption_*` | активная потребление A+ | `END01()` |
| `active_delivery_*` | активная отдача A− | `END02()` |
| `reactive_consumption_*` | реактивная потребление R+ | `END03()` |
| `reactive_delivery_*` | реактивная отдача R− | `END04()` |

`*_day` — тариф T1 (день), `*_night` — T2 (ночь), `*_total` — сумма.
Единицы — как отдаёт счётчик: кВт·ч / квар·ч. Чтение `ENDzz()` занимает до
~25-45 с каждая, поэтому в этот период опрос мгновенных значений приостанавливается
и возобновляется после снятия снимка.

## HTTP API дашборда

| Маршрут | Метод | Что отдаёт |
|--|--|--|
| `/api/ce308/current` | GET | текущий снимок CE308 (мгновенные значения + время актуальности) |
| `/api/ce308/energy` | GET | последний разовый снимок энергии (404, если ещё не было) |
| `/api/ce308/energy` | POST | сигнал снять показания энергии (200 + `accepted:true/false`; 429 при частом запросе) |
| `/api/ce308/series?from&to` | GET | история суммарной активной мощности CE308 (Redis + PG) |

## Файлы

- `ce308_client.go` — BLE-транспорт (tinygo.org/x/bluetooth, BlueZ), кадры IEC 61107.
- `ce308_agent_linux.go` / `ce308_agent_other.go` — BlueZ-агент PIN (Linux) / заглушка.
- `ce308.go` — конфиг-раздел, маппинг values, парсинг энергоснимка.
- `ce308_poller.go` — 2-с цикл, реконнект, обработка сигнала энергоснимка.
- `ce308_store.go` — Redis-ключи current/series/energy и выборка истории.
- `ce308_accumulator.go` — усреднение 10-с промежутков в PG.
- `ce308_test.go` — тесты маппинга значений и парсинга энергии.

## Замечания по эксплуатации

- Для BLE нужен поддерживающий LE-контроллер (BlueZ на Linux) и счётчик в зоне
  видимости; классический BT 2.0 (HCI 2.0) не подходит.
- Счётчик должен «вещать» по BLE (иногда требуется активировать радиоканал).
- Если устройство ещё не спарено с хостом, первое подключение выполняется
  агентом с PIN из конфига; если хост сконфигурирован иначе — потребуется
  предварительное спаривание (`bluetoothctl`).
