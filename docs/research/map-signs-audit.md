> **Историческое.** Заметка эпохи реверса; актуальные ключи/логика — в docs/modules/map-mppt.md.

> **Статус:** исследование и анализ завершены. **Рефакторинг ОТЛОЖЕН** — код НЕ
> менялся. Документ написан так, чтобы другая сессия могла подхватить работу без
> повторного реверса.
>
> **Дата:** 2026-10-10. **Контекст:** визуально сейчас всё корректно (огоньки
> анимации бегут в нужную сторону, линии тока/мощности на графиках стоят по верную

> не сломав визуал; допустимы миграции БД.

## 0. Для чего этот документ

`sunReceiver` опрашивает МАП Титанатор **двумя взаимоисключающими способами** — через
Modbus-RTU (гейт `daemons/mapgateway/`) и через legacy веб-API ПАК «Малина»
(`read_json.php?device=map`). Интерпретация знаков и типов (знаковый/беззнаковый,
точность) у этих параметров неоднократно менялась методом «подгонки под наблюдаемые
данные», из-за чего в коде накопились локальные условные/безусловные инверсии знака.
Это влияет на плашки, анимацию, графики и на историю в Redis/PG (а также на `current`,
который читают другие процессы).

Документ фиксирует: (1) целевой контракт знаков (менять не нужно), (2) реальные
кодировки ячеек МАП, (3) как каждая ветка считает величины, (4) конкретные костыли и
противоречия, (5) эталонную реализацию MicroArt, (6) открытые вопросы под замер,
(7) пофазный план рефакторинга.

## 2. Целевая семантика знаков (СОХРАНИТЬ, не менять)

Дашборд, анимация и графики уже трактуют знаки единообразно и верно (подтверждено
визуально). Это целевой физический контракт:

| Величина | Знак `+` | Знак `−` |
|---|---|---|
| `grid_power` (сеть) | потребление из сети | отдача/продажа в сеть |
| `battery_power` (АКБ) | отдача (разряд) | заряд |
| `battery_current` (АКБ) | разряд | заряд |
| `ac_active_power` инверторов/КЭС | выработка | — |

Формула мощности Дома: `HousePower = Σac(инверторы Дома) + P(сеть) + battery_power`
(`dashboard.go:1521..1539`; проверочный пример из кода: `392 + (−4551) + 7038 = 2879`).

Клиентская трактовка (для справки):
- `animation.js:447` — ребро «Счётчик→МАП» рисует `map_grid_power` (greenSign −1);
- `animation.js:455` — ребро «МАП→Сеть дома» = `house_grid_power + map_battery_power`;
- `animation.js:489..494` — ребро «МАП→Батарея» = `−map_battery_power` (заряд красный,
  отдача зелёная);
- `charts.js:506..511` — ряд `map_battery_power` инвертируется («−battery_power:
  отдача/разряд = минус, заряд = плюс»);
- `dashboard.js:535..536` — KPI `kpiBatI`/`kpiBatP` = `map_battery_current` /
  `map_battery_power`.

> **Ключевой вывод:** знаки на выходе УЖЕ правильные. Рефакторинг не должен менять
> целевые знаки — только способ их получения. Поэтому **миграции значений БД в
> базовом варианте не требуются** (см. §11).

## 3. Кодировки ячеек МАП (каталог)

По `protocol_MAP_cells_2026_07_15.doc`, `cleaning.malina/docs/map-contract.md` и
эталону `mapread.py`:

| Величина | Ячейка | Кодировка | Примечание |
|---|---|---|---|
| Напряжение АКБ | `UAcc_med_VH/VL` 0x405/0x406 | `(VH*256+VL)/10` В | VH — старший адрес |
| Ток АКБ точный | `IAcc_med_A_u16_L/H` 0x432/0x433 | `(L + H*256)/16` А; **магнитуда беззнаковая**, знак — по режиму (`MODE==4`=заряд) | см. §7 |
| Ток АКБ грубый | `IAcc_med_A_2` 0x408 | `raw*2` А (альтернатива в эталоне) | не используем |
| Ток АКБ по фазам | `I_Akb_MAP_faz1/2/3` 0x528/0x52A/0x52C (+H 0x529/52B/52D) | `(L+(H&0x7F)*256)/10` А; **знак-магнитуда: бит `0x80` в H** (0x80=отрицательный) | не используем |
| «Нагрузка по АКБ» | `PLoad_L` 0x409 (+`PLoad_H` 0x456) | `(PLoad_H*256+PLoad_L)*100` Вт — **нагрузка потребителя через АКБ**, не батарея | не используем (см. §7) |
| Мощность АКБ точная | `PLoad_8` 0x59E/0x59F | `((H<<8)|L)/8*100` Вт | не используем |
| Мощность сети | `PNET_8` 0x59A/0x59B | `((H<<8)|L)/8*100` Вт; **знак — отдельная ячейка** `PNET_Sign_P` 0x587 (`1`=потребление, `0`=отдача) | используем (Modbus) |
| Ток сети | `INET` 0x423 | беззнаковый («ток, отбираемый от сети») | используем производно |
| Ток сети точный | `INET_16_4` 0x431 | `/16` при `INET<16`, иначе `/4` (эмпирика эталона) | не используем |
| Скорость/режим | `MODE` 0x400 | 0 off, 1 off+net, 2 генерация, 3 трансляция, ≥4 заряд (`4`=«трансляция+заряд») | используем для знака тока |
| Состояние заряда | `StatusCh` 0x402 | биты: 1 буферный, 2 «надо заряжать», 4 2-я ступень, 8 3-я ступень (`cleaning.malina/docs/legacy_read_json_map.md §3`) | **кандидат** в признак заряда |
| Энергии АКБ | `M_POWhourMAP*` 0x450-0x452 (разряд), `M_POWhourMAPCharge*` 0x453-0x455 (заряд) | 24-бит | не используем |
| Энергия сети | `M_POWhourNET*` 0x44D-0x44F (беззнаковый счётчик) + `M_POWhourNET_sign` 0x592 (знаковый) | 24-бит / 32-бит | не используем |
| `_Inet_flag` | поле ПО `mapd`, НЕ ячейка МАП | косметическая инверсия знака `_INET`/`_PNET_calc` в JSON; направления НЕ несёт | см. `docs/malina-bug_Inet_flag.md` |

**Принципиально:** в МАП направление почти нигде не зашито в значение — либо отдельная
ячейка-знак (`_PNET_Sign_P`, `M_POWhourNET_sign`), либо знаковый бит (0x80 у фазных
токов), либо режим (`MODE`). Кодировки **разнородные** (беззнаковая магнитуда /
знак-магнитуда / доп. ячейка) и **разной точности** (8-бит грубый, 16-бит точный,
0.1А фазный). Это — корень путаницы.

## 4. Как считает каждая ветка sunReceiver

### Ветка A — Modbus (`mapMAPRegisters`, `srv cmdsunreceiver/main.go:1444`)
Читает байт-ячейки блоками: 0x400 на 0x20 слов (→ ячейки 0x400..0x43F) и 0x580 на
0x24 слова (→ 0x580..0x5C7) (`main.go:1769,1776`).

- `battery_voltage`/`l1_voltage` = `(0x405*256+0x406)/10` (`main.go:1447..1459`).
- `battery_current` = `(uint16(0x433)<<8 | uint16(0x432))/16`, **читается как
  беззнаковый uint16**; затем `if MODE(0x400)==4 { iAcc = −iAcc }` (`main.go:1470..1492`).
- `battery_power` = `battery_voltage × battery_current` (`main.go:1523`) — знак всегда
  согласован с током.
- `grid_power` = `((0x59B*256+0x59A)/8)*100`, знак: `if 0x587==0 → −` (`main.go:1507..1514`)
  — берётся из **сырой ячейки знака** (правильно; совпадает с эталоном).
- `grid_voltage` = `0x422==0 ? 0 : 0x422+100` (`main.go:1497..1503`).
- температуры из 0x42E/0x42F/0x430 (−50), маска отсутствия 0x43C (`main.go:1526..1547`).

### Ветка B — веб-API (`mapMAPAPI`, `mppt_api.go:462`)
Читает JSON `read_json.php?device=map`; отдельно `read_memory.php?offset=1415&count=1`
для `_PNET_Sign_P` 0x587 (`FetchPNETSign`, `mppt_api.go:398..439`).

- `battery_voltage`/`l1_voltage` = `_Uacc`.
- `grid_voltage` = `_UNET` (API уже в вольтах).
- `grid_frequency` = `_TFNET`.
- `grid_power` = `±_PNET_calc` (`= _UNET × _INET`): берётся модуль, знак — по `_PNET_Sign_P`;
  фолбэк на `_Inet_flag` (`invertGridFromInetFlag`) если ячейка недоступна
  (`mppt_api.go:499..511`).
- `battery_power` = `−_PLoad_calc` (`mppt_api.go:517`); фолбэк: `−(Uacc*Iacc)`.
- `battery_current` = `_Iacc` **напрямую** (`mppt_api.go:524..531`).
- температуры = `_Temp_Grad0/1/2` с маской `Temp_off`.

### Ключевое расхождение веток: `grid_power`
- Ветка A: источник — `_PNET` (`PNET_8`, 0x59A); по комментарию `mppt_api.go:450`
  «сырое `_PNET` у МАП сильно занижено (~×5 против счётчика)».
- Ветка B: источник — `_PNET_calc` (`_UNET × _INET`), «достоверная, сходится со
  счётчиком».

То есть при переключении `map.disabled` (Modbus ↔ API) тег `grid_power` меняет и
**физический источник**, и **масштаб**. Знак согласован (обе → «+ потребление»), но
магнитуда — нет.

## 5. Найденные «костыли» и противоречия

1. **Знак тока/мощности АКБ из `MODE==4`** (`main.go:1470..1492`). Ветка A читает
   0x432/0x433 как беззнаковую магнитуду и берёт знак из режима. Это **точный порт
   эталона MicroArt** (см. §7), т.е. не самодельный хак, но эвристика, покрывающая
   только основной заряд (`MODE==4`). При заряде в не-4 режиме (ЭКО-подкачка, режимы
   13/14/16/17) или при простое знак может быть неверным.
2. **`battery_current` и `battery_power` в ветке B — из РАЗНЫХ полей API**
   (`_Iacc` и `_PLoad_calc`), знаковые базы которых в самом `mapd` различны.
3. **Фолбэк знака `grid_power` по `_Inet_flag`** в ветке B (`mppt_api.go:507`) —
   устаревшая эвристика (флаг динамический, направления не кодирует); оставлена на
   случай недоступности `read_memory.php`. См. `docs/malina-bug_Inet_flag.md §9`.
4. **Подмена P(сети) счётчиком** в формуле Дома: `house_grid_power` = `meter_active_power`,
   если снимок счётчика не старше `meterGridMaxAge=20 с`, иначе `grid_power` МАП
   (`dashboard.go:60,1456..1470,1535`). Кросс-источниковая подмена по времени.
5. **Комментарии в коде противоречат друг другу и коду**: `mapRaw.Iacc` описан как
   ««+» = разряд, «−» = заряд» (`mppt_api.go:304`), а ниже тот же `_Iacc` через
   `_PLoad_calc` — как «разряд `_Iacc=+64` ↔ `battery_power=+3382`» (`mppt_api.go:526..528`).
   Тест `TestMapMAPAPIChargeSign` зашивает `_Iacc="-3.9"` при `_PLoad_calc="200"`
   (разнонаправленные знаки) — т.е. тест фиксирует расхождение, а не устраняет.

### Контрпример: `_Uacc` — эталон корректной работы
Напряжение АКБ читается одинаково в обеих ветках и совпадает со счётчиком — пример
того, как должно быть у всех величин.

## 6. АКБ отдельно (токи и мощности) — детально

### 6.1. Свидетельство противоречивости полей API
Живой снимок `read_json.php?device=map` (`docs/read_json.md`, 2026-09-07, `fw=3.7`,
`_MODE=17`):

```json
"_Uacc":"52.0", "_Iacc":"4", "_IAcc_med_A_u16":"-3.9", "_I_acc_avg":"-3.9",
"_I_acc_3ph":"3.9", "_P_acc_3ph":"202", "_PLoad":"-200", "_PLoad_calc":"-204.8"
```

Одна и та же физическая величина (~3.9…4 А) в **одном ответе** показана как `+4`
(`_Iacc`, `_I_acc_3ph`) и как `−3.9` (`_IAcc_med_A_u16`, `_I_acc_avg`). При этом
`_PLoad_calc=−204.8 ≈ 52×(−3.9)` (выведена из `_IAcc_med_A_u16`), а `_P_acc_3ph=202 ≈
52×3.9` (выведена из `_I_acc_3ph`). Значит **внутри `mapd` знаки разных полей
взаимно противоречивы**, и опираться на них без ground-truth нельзя.

### 6.2. Как это «случайно» согласуется в ветке B
`battery_power = −_PLoad_calc` (минус на отрицательное `_PLoad_calc` → «+») и
`battery_current = _Iacc` (уже «+») в примере совпали — но это результат двух
независимых флипов, а не вывода мощности из тока. Коммит `b561d25` именно «подогнал»
ток под мощность.

### 6.3. Что делает эталон MicroArt (`mapread.py:134..144`)
```python
map_IACC = (regs[0x432] + regs[0x433]*256)/16   # БЕЗЗНАКОВАЯ магнитуда
map_UACC = (regs[0x405]*256 + regs[0x406])/10
if map_MODE == 4:                               # заряд
    map_PLOAD = round(map_IACC * map_UACC)      # + заряд
else:
    map_IACC = -map_IACC; map_PLOAD = -map_PLOAD  # − разряд
```
- Подтверждает: 0x432/0x433 — **беззнаковая магнитуда**, знак — по `MODE==4`.
- Вендорская конвенция: **`+` = заряд, `−` = разряд** — **обратна** нашему контракту
  (мы инвертируем намеренно).
- Вендор **перезаписывает** `_PLoad` значением `I×U` в режиме заряда — т.е. `_PLoad`
  из ячеек 0x409/0x456 ненадёжен как «мощность батареи» (наш код это учитывает,
  отвергая `_PLoad`).

### 6.4. Проблемы АКБ (сводка)
1. Разные источники: Modbus — 0x432/0x433 (+`MODE`); API — `_Iacc` (ток) и
   `_PLoad_calc` (мощность) как **разные** поля.
2. Точность рассинхронизирована: `_Iacc` грубее (`"4"`), `_PLoad_calc`/`_IAcc_med_A_u16`
   точнее (`"−3.9"`).
3. Знаки полей API противоречивы (§6.1).
4. `MODE==4` покрывает только основной заряд (§5.1).
5. `battery_current` на дашборде почти не используется: AGM-страница
   (`dashboard.go:2569..2611`) берёт `battery_power/battery_voltage` и **сама считает
   `I = P/U`**, игнорируя `battery_current` — косвенный признак недоверия к тегу.
6. Не задействованы более информативные источники: фазные токи 0x528+ (со знаковым
   битом 0x80) и точная мощность `PLoad_8` 0x59E/0x59F.

### 6.5. Предложение по АКБ
- Единый источник тока — точный `IAcc_med_A_u16` (0x432/433) в **обеих** ветках
  (в API — `_IAcc_med_A_u16`, не `_Iacc`).
- `battery_power` **вычислять** как `battery_current × battery_voltage` (не читать
  `_PLoad`/`_PLoad_calc`/`PLoad_8`) → ток и мощность гарантированно согласованы.
- Знак — из **явного носителя**, а не только `MODE==4`: кандидаты `StatusCh` (0x402),
  проверить наличие знакового бита/ячейки у 0x432/433 (аналог 0x80 у фазных 0x528).
  Требуется замер (§8).
- Опционально: `PLoad_8` (0x59E/59F) и/или фазные 0x528+ как кросс-проверка.
- Целевые знаки АКБ не менять → миграции БД по АКБ не нужны.

## 9. План рефакторинга (ОТЛОЖЕН; исполнять после §8)

**Фаза 0 — стенд (без кода).** Снять синхронные замеры (§8), составить таблицу
кодировок/знаков. Артефакт — новый doc или приложение к этому.

**Фаза 1 — единый слой контракта.** Новый модуль (напр. `internal/mapcontract/`) с
**одной** функцией «сырые ячейки → `valuesContract`» и **одной** «поля API →
`valuesContract`», приводящими к одному внутреннему представлению. Явные типизированные

локальных инверсий «по обстоятельствам»: знак — только из явного носителя
(ячейка-знак / знаковый бит / двух'с-комплемент во значении).

Решить канон `grid_power` (§8.2) и привести обе ветки к нему (напр. `V×I` + `_PNET_Sign_P`).

**Фаза 3 — декодофикация.** Заменить разрозненные `parseFloat`, `(L+H*256)/16`,
`(H*256+L)/8*100`, унарные `−` на декодеры из Фазы 1.

**Фаза 5 — периферия.** Решить про точный ток сети `INET_16_4` (0x431) вместо `INET`

## 10. Что НЕ трогать / риски

- **Целевые знаки** (§2) не менять — визуал корректен.
- **КЭС/MPPT** (`mapMPPTAPI`) — знаки тривиальны (величины ≥0), отдельный рефакторинг
  не нужен.
- **Deye/Sofar** — знаки уже корректны; `Deye grid_power` (0xCB) в контракт не
  маппится (`main.go:1197`), конфликтов с МАП нет (разные ключи устройств).
- **Риск:** несогласованный **масштаб `grid_power`** между ветками (×5). При
  переключении `map.disabled` в истории Redis/PG будет излом. Это единственная
  потенциально «дорогая» миграция (см. §11).
- **Правила репо:** коммит/push — только по явному запросу; BMS-опрос и изменения
  `enBms` — только с согласования; приватные данные — в `.kilo/` и `sunReceiver.json`
  (в git не выгружаются); перед коммитом — проверка на секреты/приватные адреса.

## 11. Миграции БД (если/когда понадобятся)

Поскольку целевые знаки сохраняются, **в базовом сценарии миграций нет**. Миграции
потребуются только если:
- решим сменить **масштаб** `grid_power` (переход ветки A на `_PNET_calc`/V×I) —
  пересчёт истории `grid_power` МАП в окне, где источник менялся;
- решим изменить **знак** какого-либо тега (не планируется).

Образец точечной миграции (бэкап + инверсия в окне) — `docs/malina-bug_Inet_flag.md §7`:
- Redis `sunreceiver:series:<YYYY-MM>` и PG `sunreceiver.averages` (устройство МАП);
- бэкап-ключ/таблица (`…:bak-migr<дата>`, `…_bak_migr<дата>`), идемпотентный критерий
  отбора точек.
