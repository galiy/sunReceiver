## ТРЕК A — Данные и дашборд

### Критичные

#### A1. K1 — BMS: валидно-пустой ответ стирает весь дашборд батарей
> **✔ Выполнено** (bms_poller.go — счётчик `bmsEmptyStreak`, порог `bmsEmptyTolerance=3`).
Файлы: `bms_poller.go`, `redis_store.go`.
Проблема: `pollAndSaveBMS` (bms_poller.go:209-229) защищается только от
`col.Updated == 0`, но `{"updated">0, "devices":[]}` (HTTP 200) проходит гвард →
`SetBMS(empty)` (redis_store.go:256-278) HDEL-ит всё.

Решение (устойчивая пустота + TTL-подобный гвард):
- Ввести в `pollAndSaveBMS` счётчик подряд идущих **валидно-пустых** ответов
  (`updated>0 && len(devices)==0`). Пока счётчик < `bmsEmptyTolerance` (константа,
  напр. **3** — ~3 секунды подряд) — **не вызывать** `SetBMS` и **не** чистить:
  возвращать `col`, но пропускать запись в Redis (аккумулятору `acc.add` —
  оставлять, безопасно).
- При достижении порога/превышении — разрешить `SetBMS` (реальный уход устройств).
- Пока пустота «неустойчива», **не удалять** существующие устройства: это и есть
  гвард. Перезапуск `bmslistener` / временная пустота shm — одиночные/короткие,
  порог их не пропускает.
- Сброс счётчика: при любом ответе с `len(devices)>0` → 0.

Приёмка: при `{"updated">0,"devices":[]}` 1–2 раза подряд HASH `sunreceiver:bms`
и серия сохраняются; при устойчивой пустоте (>3) — очищаются. Тест на
`pollAndSaveBMS`: подаём пустой ответ → `HGetAll(bms)` не пуст.

#### A2. K2 — MPPT: пустой ответ `read_json.php?device=mppt` чистит все контроллеры
> **✔ Выполнено** (main.go `pollAndSaveMap` — счётчик пустых ответов, порог `mpptEmptyTolerance=3`).
Файлы: `main.go` (`pollAndSaveMap`, 1268-1333), `redis_store.go` (`PruneMPPT`, 221-250).
Проблема: `fetchOK=true` ставится при `err==nil`, даже если `arr=[]` →
`activeMPPT` пуст → `PruneMPPT(empty)` (main.go:1331-1332) HDEL-ит все `#mppt`.

Решение (тот же гвард устойчивости):
- В `pollAndSaveMap` вести счётчик подряд идущих **пустых** (`len(arr)==0`) успешных
  ответов. Пока счётчик < `mpptEmptyTolerance` (константа, напр. **3**) — **не
  вызывать** `PruneMPPT` (запись текущих снимков в `current` — оставлять; просто
  пропустить прунинг).
- При пороге — вызвать `PruneMPPT` (реальный уход всех контроллеров).
- Сброс при `len(arr)>0` → 0.
- Не менять семантику: МАП-запись снимков (SaveSnapshotWindow) остаётся как есть.

Приёмка: `arr=[]` 1–2 раза не роняет существующие `#mppt`-ключи `current`; после
устойчивой пустоты — чистит. Тест: `pollAndSaveMap` с пустым ответом сохраняет старые ключи.

#### A3. K3 — BMS: потеря полноты 5-минутного бакета при рестарте
> **✔ Выполнено** (drain неполного бакета только в Redis; `InsertBMSAveraged` — sample-count guard).
Файлы: `bms_accumulator.go` (drain, 232-239), `pg_store.go` (`InsertBMSAveraged`,
199-213), `bms_poller.go` (вызов drain, 162 / `saveBMSClosedBuckets`, 171-191).
Стратегия (выбрано): **Sample-count guard + не делать drain в PG**.

1. **Не делать drain в PG:** при остановке (`partial=true`) неполный бакет писать
   **только в Redis** (`SaveBMSSeries`), **не в PG** (`InsertBMSAveraged`). Для этого
   в `saveBMSClosedBuckets` (bms_poller.go:171-191) при `partial==true` пропускать
   PG-ветку. PG получает только полные 5-мин бакеты.
2. **Sample-count guard в `InsertBMSAveraged`:** изменить SQL upsert так, чтобы
   НЕ перетирать существующую строку, если она не менее полна:
   `ON CONFLICT (name, ts) DO UPDATE SET values = EXCLUDED.values
    WHERE sunreceiver.bms_averages.values->>'samples' IS NULL
       OR (EXCLUDED.values->>'samples')::int > (sunreceiver.bms_averages.values->>'samples')::int`
   → перезапись только когда новая запись содержит **больше** сэмплов. Это
   предпочтительно для конкурентного дописывания (живые бакеты), где поздняя запись
   может быть полнее.
   - Требует, чтобы `bmsAveraged.Samples` всегда сериализовался в jsonb
     `values` (уже есть, поле `samples json`). Проверить, что `Samples` не теряется
     при marshal (json: `samples`).
3. Приложить к этому комментарий в `InsertBMSAveraged`, раскрывающий эффект при
   рестарте (сейчас в pg_store.go:191-198 эффект потери не раскрыт).
4. Опционально (для Redis `SaveBMSSeries`): т.к. PG защищён sample-guard, Redis-ряд
   остаётся last-write-wins — допустимо, но стоит **не** писать неполный drain-бакет
   в Redis тоже, если он «перетрёт» более полный (см. A3 п.1 — Redis пишем только
   если это не регресс). Принято: Redis-точку drain оставляем (это единственное
   представление «момента остановки»), PG — guard.

Приёмка: рестарт посреди бакета: PG-запись остаётся от более полного (предыдущего
полного либо нового полного) бакета; `InsertBMSAveraged` с меньшим `Samples` не
перетирает большее. Тест: юнит-тест SQL-ветки (mock pgx или интеграционный на
поднятой БД — предпочтительно проверка эквивалентного поведения через
`pgxmock`/реальный PG в тест-скелете, если есть; иначе — логическая проверка).

### Важные

#### A4. V1 — BMS: коллизия имён по `DeviceName`
> **✔ Выполнено** (ключ `deviceName@Port` ТОЛЬКО при коллизии имён; поле `Display`; регрессия истории исправлена коммитом `cce3a2c`).
Файлы: `bms_poller.go` (213-224), `bms_accumulator.go` (186, 199-211),
`redis_store.go` (292, 298, 353), `dashboard.go` (2592, 2606, 2686).
Проблема: ключ/серия = `deviceName` (`"AntBms 320 A/h"`), две одинаковые — сливаются.

Решение: ключевать по **`Port`** (стабильный USB-порт адаптера) или
`DeviceName + "|" + Port`, когда есть смысл. Поскольку `Port` — позиционный
идентификатор адаптера и может быть пустым, использовать функцию
`bmsKey(d bmsDevice) string`:
- если `d.Port != ""` → `d.DeviceName + "@" + d.Port`
- иначе → `d.DeviceName` (фолбэк, сохраняем текущее поведение).

Применить везде, где сейчас используется `DeviceName` как ключ:
`active[DeviceName]` → `active[bmsKey]` (bms_poller.go:224), `buckets[DeviceName]`
(bms_accumulator.go:204, 207), `bmsSeriesPoint.Name` (bms_poller.go:176),
`QueryBMSSeries(name)` / `BMSOne(name)` (redis_store.go), дашборд-хендлер
`/api/bms/{name}` (dashboard.go:2606) и сортировка (2592).
Внимание: `Name` в `bmsSeriesPoint`/`bmsAveraged` — это уже ключ, а не displayName.
Ключ отображается на дашборде как заголовок: **вынести отображаемое имя** отдельно —
в `bmsDevice` добавить понятный label (или хранить `DeviceName` в JSON точки, а
ключ — в отдельном поле). Решение: `bmsSeriesPoint{Name:<ключ>, Display:<deviceName>}`;
дашборд читает `Display` для заголовка, `Name` — для запросов.

Приёмка: две одинаковые батареи с разными `Port` дают разные HASH-поля и разные ряды;
заголовок на дашборде — исходный `DeviceName`.

#### A5. V2 — MPPT без UID: стабильный ключ вместо индекса
> **✔ Выполнено кодом** (маппинг слот→UID `mpptPollState.resolveUID`); **требует подтверждения на живом железе**.
Файл: `main.go` (1307-1319), `devKey` (339-350).
Проблема: `devKey` при пустом `UID` использует `Slot` → отвал нижнего слота сдвигает
ключи. Требует знания реальных полей API (гипотеза в ревью).

Решение (код, подтверждение на проде):
- Сначала исследовать реальный ответ `read_json.php?device=mppt` на живом железе
  (или в логах/собранных примерах в `docs/research/`) — найти стабильный идентификатор
  (напр. `SN`, `MODEL`, `id`).
- Если есть стабильный id — использовать его в `devKey` вместо `Slot`.
- Если нет — сохранить поведение, но добавить **маппинг `слот→ключ`** в памяти
  (`map[slot]uid`), чтобы при пустом `UID` ключ не «дрейфовал» между опросами: после
  первого опроса запомнить `slot→фактический UID` и переиспользовать.
- Открытая гипотеза V2 помечается в плане как требующая живого железа; реализуем
  код-маппинг, а финальное поле уточняется на проде.

Приёмка: при пустом `UID` ключ устройства стабилен между опросами (не сдвигается
при отвале слота). Покрыть юнит-тестом `devKey`/`pollAndSaveMap` при пустом UID.

#### A6. V3 — Deye `ac_reactive_power` (0x58) — знак
> **✔ Выполнено кодом** (`Signed:true`); **требует подтверждения на живом железе**.
Файл: `main.go` (730, 763-768).
Решение: установить `Signed:true` для 0x58. `float64(int(int16(v)))*0.1` даст
отрицательное при `raw>=0x8000`. Проверить на живом железе (гипотеза).
Риск: у существующих данных знака не было; после правки значение может стать
отрицательным для случая, который раньше читался как большое положительное.
Приёмка: регистр 0x58 парсится знаково; на живом железе при отрицательной реактивной
мощности отображается отрицательное значение (проверка вручную после деплоя).

#### A8. V5 — modbusmap: валидация Transaction/Unit ID
> **✔ Выполнено** (`modbusmap/client.go` — сверка txn/unit, `closeConn` при несовпадении).
Файлы: `modbusmap/client.go` (93-99, 119-143).
Решение: в обработке ответа сверять:
- `binary.BigEndian.Uint16(hdr[0:2]) == c.nextTxn()` — но т.к. `nextTxn()` инкрементит,
  сохранить значение использованного txn при построении запроса; сверять с ним.
- `hdr[6] == c.Unit`.
При несовпадении — `c.closeConn()` и возвращать ошибку (поздний ответ от старого
запроса на переиспользуемом сокете не принимается).
Приёмка: юнит-тест: ответ с неверным txn/unit → ошибка + закрытие соединения;
верный → данные ячеек.

#### A9. V7 — гонка `restoreRedisFromPG` ↔ `backfillAccumulator`
> **✔ Выполнено** (`restoreRedisFromPG` синхронно до запуска `runAccumulator`).
Файлы: `main.go` (1436-1463, запуск горутин), `accumulator.go` (239, `backfillAccumulator`).
Решение: сделать реставрацию **синхронной до запуска аккумулятора**:
- Запускать `restoreRedisFromPG` в фоне, но перед `runAccumulator` — ждать его

Приёмка: backfill читает полностью восстановленный Redis; нет перетирания полных
PG-бакетов частичными.

#### A10. V8 — PG-запись бакетов без транзакции/retry
> **✔ Выполнено** (`retryPg`/`withTx` — транзакция + retry 100/500/1000мс для инверторов и BMS).
Файлы: `accumulator.go` (118-156), `bms_poller.go` (171-191), `pg_store.go` (124-139, 199-213).
Решение:
- **Инверторный** `insertAverageBucket`: обернуть все `InsertAveraged` одного бакета
  в одну **транзакцию** (`pgx` `BeginTx`/`pg.Tx`), с ограниченным **retry**

  Параллельные бакеты оставить (bucketWg), но транзакция в каждом.
- **BMS** `saveBMSClosedBuckets`: аналогично — batch/tx на набор точек одного вызова.
- Добавить хелпер `retryPg(fn, attempts)` в `pg_store.go` (или общий `retry`).
Приёмка: краткий сбой PG не оставляет «дыру»: retry дописывает бакет; инверторный
набор точек пишется атомарно (все или ничего).

#### B2. V14+V15 — `logfile_windows.go`: ротация + fallback на %LOCALAPPDATA%
> **✔ Выполнено** (ротация по 10МБ `rotatingWriter` + fallback exe-dir → LOCALAPPDATA → TempDir).
Файл: `logfile_windows.go` (30-47).
Решение:
- **Ротация по размеру:** в `setupLogging` открывать файл; перед открытием (и затем
  периодически/при каждой записи через обёртку) проверять размер; при превышении
  `logMaxSize` (напр. 10 МБ) — переименовать `sunReceiver.log` →
  `sunReceiver.log.1` (переоткрыть). Простейшее — обернуть `log.SetOutput` в
  кастомный `io.Writer`, который переоткрывает файл по размеру.
  Альтернатива без обёртки: `log.SetFlags` + периодическая проверка в фоновой
  горутине не подходит (логгер пишет долго). Рекомендуется обёртка `rotatingWriter`.
- **Fallback на `%LOCALAPPDATA%`:** в `logFilePath()` при недоступности пути рядом с
  exe (или при ошибке OpenFile) — пробовать `os.UserCacheDir()` / `%LOCALAPPDATA%`
